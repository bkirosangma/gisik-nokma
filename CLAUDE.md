# gisik-nokma

Project management software ("the keeper of memory" — Garo: *gisik* mind/memory, *nokma* the custodian who holds things in trust). Based on the convenience-corner project tracker, snapshotted verbatim under `reference/` at upstream commit `24e2240`.

**Status: pre-brainstorm.** No product decisions exist. The first working session runs `superpowers:brainstorming` from `docs/brainstorm-kickoff.md` — do not scaffold apps, pick stacks, or write product code before that design session concludes and its spec is approved.

## Rules

- **A merge to `main` deploys to production. Work happens on release branches.** (Owner, 2026-09-23.) `deploy/do/app.yaml` sets `deploy_on_push: true` against `branch: main` on all three components — the `server` service (`:50`), the `web` service (`:222`) and the `backup` worker (`:248`) — so *any* push to `main` ships to the live app within minutes. A one-line docs fix deploys exactly as a feature does; nothing about a diff's size or subject exempts it, and there is no staging hop in between. So `main` is no longer where work integrates:
  - **Cut a release branch** from `origin/main` — `release/<YYYY-MM-DD>` (the first is `release/2026-09-23`), distinct from the per-task `rel/*` branches the release plan used.
  - **Feature, fix and docs branches PR into the live release branch**, not into `main`. The release branch accumulates until the owner says it is ready. **The shape of an ordinary task** (owner, 2026-09-23 — *"for tasks do remember to branch out from the release branch and merge back into it"*): branch off the live release branch → work → PR `--base release/<date>` → **a LOCAL run green, named as local** → merge back into the release branch. **CI does not run on a dev PR** (owner, 2026-09-23): `ci.yml` filters `pull_request` on the BASE branch, so only the release→`main` PR runs the pipeline. This repo is private and every minute is billed, and the whole point of the release branch is that one gate before the deploy rather than fourteen checks per task branch. The cost is real and is the trade the owner took: work lands in the release branch unverified by anything but its own author's run, so run the suites and say *which* run you are quoting. `workflow_dispatch` is there when a change is big enough to be worth the minutes. The heavy `ctl checks`/`ctl gate`/`ctl land` bar is **not** the bar for that merge — those verbs read `origin/main` and exist for the release→`main` landing, which is the deploy.
  - **Merging the release branch to `main` IS the release** — the act that deploys. It happens on the owner's word, per merge, every time.
  - **The dev stack is built from the release branch** (owner, 2026-09-23), so the owner can verify what is about to ship before it ships. `ctl rebuild` pulls and builds the primary checkout's *current* branch, accepting `main` or `release/*` and refusing a task branch or a detached HEAD. The stack still runs from the primary checkout — that folder alone holds `.env` and the baked build args — so only the branch moved, not the folder (`Features.md`, "The dev stack serves BUILT images"; cases 13.1347–13.1350).
  - **The standing auto-merge authorization is retargeted, not revoked:** it covers merges *into a release branch* only. **No standing authorization covers a merge to `main`** — that one is owner-approved each time, because it ships.
  - Known consequences, not yet fixed: `ctl gate`, `ctl land` and `ctl check-pr` all read `origin/main` as the integration ref (`scripts/ctl/verbs/gate.sh:20`, `verbs/land.sh:23`, `verbs/check-pr.py:11`), so they cannot land a PR based on a release branch — they refuse on the ancestry and tree checks rather than mis-merge, and making them `--base`-aware is an open task. CI runs on the release→`main` PR and on a push to `main`, and **not** on a dev PR into a release branch — `ci.yml`'s `pull_request` trigger filters on the PR's BASE. The release PR's run happens BEFORE the merge, which is the point: a merge to `main` is already deploying by the time a post-merge job could start.
- **Never commit or push to `main`.** `main` is unprotected — this is a free private repo, the same position convenience-corner is in — so nothing on the server will stop a direct push, and since 2026-09-23 a push there also deploys (above). Every change goes on a branch, through a PR, merged only with the owner's approval — given per-PR, or, **for merges into a release branch only**, through the **standing auto-merge authorization** recorded in the coordination doc's autonomous execution protocol (2026-08-28: PRs that passed the full machinery AND an independent CI run green; owner notified after each merge; authorization revocable in a word). Treat the branch rule as the protection GitHub would otherwise enforce: check the current branch before any `git commit` or `git push`, and if it is `main`, branch first.
- **`reference/` is frozen.** Never edit anything under it. The base lives upstream in `convenience-corner`; corrections happen there and get re-snapshotted with a new commit reference recorded in `reference/convenience-corner-tracker/PROVENANCE.md`.
- **Never pipe a test or build run into `head` (or `grep -m N`).** `head` closes the pipe as soon as it
  has its lines; the runner's parent dies on EPIPE and its fork workers are orphaned at `ppid=1`, spinning
  at ~1 core each and growing. On 2026-09-04 `cd apps/web && pnpm exec vitest run 2>&1 | head -6` returned
  "success" in 2.5 s and left six vitest workers behind; twenty-three minutes later they held 22.4 GB on a
  16 GB machine, and three kernel jetsam events and a forced restart followed. Reproduced on demand.
  Use `| tail -N`, or `> /tmp/run.log 2>&1; head -N /tmp/run.log`, or a `grep` with no `-m`. After any run
  that returned suspiciously fast or was cut short, reap ORPHANED workers only — `ps -eo pid=,ppid=,comm=,args= | awk '$3 ~ /node$/ && $2 == 1 && index($0, "vitest") > 0 {print $1}'` (ppid=1 = reparented to launchd) — before
  calling the step done. **Never `pkill -f vitest` and never kill `pgrep -f vitest`'s output**: when
  Claude sessions run with this file in their prompt, their own command lines contain the word "vitest",
  so `pgrep -f vitest` names every such session plus every peer's live workers (measured 2026-09-06: five
  sessions and a live 10-worker pool, zero orphans). Read the list
  calling the step done. **A `PreToolUse` hook on this machine now refuses the piped form**
  (`~/.claude/scripts/no-piped-test-runs.py`, registered in `~/.claude/settings.json`); it is machine-local,
  so a fresh machine needs it installed again — the rule above is the part that travels.
- **Features.md and `test-cases/` stay in sync with reality** per the workspace conventions (`/Users/kiro/my_projects/CLAUDE.md`) — same change set, never a follow-up.
- The base's load-bearing ideas are summarised in the README; treat them as *informed starting points* for the brainstorm, not as decisions already made for the product.
