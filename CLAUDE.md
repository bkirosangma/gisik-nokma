# gisik-nokma

Project management software ("the keeper of memory" — Garo: *gisik* mind/memory, *nokma* the custodian who holds things in trust). Based on the convenience-corner project tracker, snapshotted verbatim under `reference/` at upstream commit `24e2240`.

**Status: live in production** (DigitalOcean App Platform, go-live 2026-09-22). What ships is catalogued in `Features.md`, its scenarios in `test-cases/`, designs and plans in `docs/superpowers/specs/` and `docs/superpowers/plans/`, and owner-paused work in `docs/held-work.md`. New features still start with `superpowers:brainstorming` and an owner-approved spec.

## Rules

- **A merge to `main` deploys to production. Work happens on release branches.** (Owner, 2026-09-23.) `deploy/do/app.yaml` sets `deploy_on_push: true` on `branch: main` for `server` (`:50`), `web` (`:222`) and `backup` (`:248`): any push to `main` — a one-line docs fix included — ships within minutes, with no staging hop.
  - **Release branch:** cut `release/<YYYY-MM-DD>` from `origin/main` (the first was `release/2026-09-23`; not the per-task `rel/*` branches).
  - **A task** (owner: *"for tasks do remember to branch out from the release branch and merge back into it"*): branch off the live release branch → work → PR `--base release/<date>` → **a LOCAL run green, named as local** → merge into the release branch. The release branch accumulates until the owner says it is ready.
  - **CI does not run on a dev PR** (owner, 2026-09-23): `ci.yml` filters `pull_request` on the BASE branch, so only the release→`main` PR (before the merge, which is the point — a merge to `main` is already deploying) and a push to `main` run it. The repo is private and every minute is billed; one gate before the deploy beats a check per task branch. Work lands in the release branch verified only by its author's run, so run the suites and say *which* run you are quoting. Use `workflow_dispatch` when a change is big enough to be worth the minutes.
  - **Merging the release branch to `main` IS the release.** It happens on the owner's word, per merge, every time. `ctl gate <sha>` / `ctl land <pr>` with no `--base` are the bar for that landing.
  - **Reviews and merges INTO the release branch are autonomous** (owner, 2026-09-23: *"automatically take care of the reviews and merges"*). The bar is not lowered by the authorization: the reviewer reads the diff against the brief's pinned shape and runs the LOCAL battery itself (build → typecheck → affected suites → catalogue checks) rather than trusting the lane's report, and reports it as a local run. **This does NOT reach `main`.**
  - **The dev stack is built from the release branch** (owner, 2026-09-23). `ctl rebuild` builds the primary checkout's *current* branch — `main` or `release/*`, refusing a task branch or detached HEAD. The stack still runs from the primary checkout, which alone holds `.env` and the baked build args (`Features.md`, "The dev stack serves BUILT images"; cases 13.1347–13.1350).
  - **Landing into a release branch:** `ctl gate <sha> --base release/<date>` then `ctl land <pr> --base release/<date>` — both measure against `origin/release/<date>`, a release-kind marker can never satisfy a landing to `main`, and `land` must be given the same `--repo` the gate ran in (the marker is per checkout) (`scripts/ctl/README.md:8-14`). A worktree's `pnpm install` must run under Node 22.
- **Never commit or push to `main`.** It is unprotected (free private repo, like convenience-corner), so nothing server-side stops a direct push — and a push deploys. Check the current branch before any `git commit` or `git push`; if it is `main`, branch first. Every change goes through a PR merged with the owner's approval — per-PR, or, **for merges into a release branch only**, the standing auto-merge authorization in the coordination doc's autonomous execution protocol (2026-08-28: PRs that passed the full machinery AND an independent CI run green; retargeted 2026-09-23; owner notified after each merge; revocable in a word). **No standing authorization covers a merge to `main`.**
- **`reference/` is frozen.** Never edit it. Corrections happen upstream in `convenience-corner` and are re-snapshotted with the new commit recorded in `reference/convenience-corner-tracker/PROVENANCE.md`.
- **Never pipe a test or build run into `head` (or `grep -m N`).** `head` closes the pipe; the runner dies on EPIPE and its fork workers are orphaned at `ppid=1`, each spinning ~1 core. On 2026-09-04 `pnpm exec vitest run 2>&1 | head -6` "succeeded" in 2.5 s and left six workers that reached 22.4 GB on a 16 GB machine (three jetsam events, a forced restart). Use `| tail -N`, `> /tmp/run.log 2>&1; head -N /tmp/run.log`, or `grep` without `-m`.
  - After a run that returned suspiciously fast or was cut short, reap ORPHANED workers only: `ps -eo pid=,ppid=,comm=,args= | awk '$3 ~ /node$/ && $2 == 1 && index($0, "vitest") > 0 {print $1}'`.
  - **Never `pkill -f vitest` or kill `pgrep -f vitest`'s output**: Claude sessions with this file in their prompt have "vitest" in their own command lines (measured 2026-09-06: five sessions and a live 10-worker pool, zero orphans). Read the list before killing anything.
  - A machine-local `PreToolUse` hook (`~/.claude/scripts/no-piped-test-runs.py`, in `~/.claude/settings.json`) refuses the piped form; a fresh machine needs it reinstalled — the rule is the part that travels.
- **Features.md and `test-cases/` stay in sync with reality** per the workspace conventions (`/Users/kiro/my_projects/CLAUDE.md`) — same change set, never a follow-up.
- The base's load-bearing ideas are summarised in the README; treat them as *informed starting points* for the brainstorm, not decisions already made for the product.
