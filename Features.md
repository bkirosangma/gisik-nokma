## 3. Foundation & event ledger

- ⚙️ **Monorepo workspace** — pnpm workspaces + Turborepo, TypeScript strict, Node 22, ESM, Vitest; packages `@gisik-nokma/domain`, `@gisik-nokma/rule-engine`, `@gisik-nokma/server`, `@gisik-nokma/ui`, `@gisik-nokma/app-core`, `@gisik-nokma/sync-client`. Root configs `pnpm-workspace.yaml`, `turbo.json`, `tsconfig.base.json`; dev Postgres via `docker-compose.yml`.
- ⚙️ **CI pipeline (skeleton)** — GitHub Actions workflow on every pull request and push to `main`: a single job installs via pnpm, brings up a Postgres 16 service container matching `docker-compose.yml`'s user/password/port, and runs the turbo gate (`build`, `test`, `typecheck`); IST convergence rides the same per-test-database `ALTER DATABASE` the test harness already runs, not a container-level override. The independent-CI precondition for the coordination doc's auto-merge protocol. Scoped to what Plans 1–2 landed — lint, `check:env` (Plan 11 T6), the client half of the fixtures suite and the dual-client job (Plan 10), the e2e job (Plans 4/6), and the interim-plumbing gate (Plan 10) land with their owning plans; Plan 11's own catalogue task owns the full pipeline under §13. `.github/workflows/ci.yml`
- ⚙️ **Event envelope & vocabulary** — the exact `EventEnvelope` contract with zod validation, ULID helpers, and the versioned event-type registry; pure `parseEvent` refuses unknown types, unknown versions, invalid payloads, malformed envelopes, and — for a registration that declares an `entityKind` — an envelope whose `entity.kind` differs (`entity-kind-mismatch`; layered with the rule engine's own kind checks by design, since fixtures and offline replicas bypass `parseEvent`). Provisional seed vocabulary: `workspace.created` v1, `workspace.renamed` v1; the registry now also holds `workflow.defined` v1 (Plan 2). `packages/domain/`
- ⚙️ **Contest event vocabulary** — `claim.contested` v1 and `claim.contested_resolved` v1, the two types that make a sync-time refusal into ledger history instead of a silent drop (spec honesty invariant 5, coordination amendment 16). The contest carries the refused claim whole (`originalEvent`, a full `SubmittedEvent`) and is refused if the claim arrives without its `payload` — `z.unknown()` makes that key optional in zod, so the envelope door's own payload-presence check (Plan 4's amendment) is what stops the ledger from recording that something was claimed without recording what. `null` and `{}` still pass: an empty claim is a claim, an absent one is not. Resolution is `redone` | `converted-to-comment` | `discarded`, and the first two must link the event they produced — a redo without its replacement id, or a conversion without its comment id, is refused. Both types bind `entityKind: 'ticket'` in the registry, so a contest filed against a workflow or a workspace is refused at the door with `entity-kind-mismatch` rather than appended to an append-only table where it could never be corrected. Alongside them: `renderContestedClaimText(payload)`, the one attributed, IST-dated, rule-naming sentence a banner shows and a "convert to comment" writes into the ledger forever, and `plainTextToDoc(text)`, the inverse of `docToPlainText` — the minimal ProseMirror doc that conversion needs because bodies are PM JSON. `packages/domain/src/events/contest-events.ts`, registrations in `packages/domain/src/vocabulary.ts`
- ⚙️ **Client envelope builder** — `newSubmittedEvent(...)`, the one place a client mints an event: it fills `id` (ULID), `version` and `clientTime` and copies the rest of the caller's claim. `serverTime` and `seq` are absent by construction, because they are the server's to assign at ingest and a client that invented them would be asserting facts it does not own. `packages/domain/src/submit.ts`
- ⚙️ **IST day boundaries** — `istDayOf(instant)` and `istDayBounds(day)` against the fixed +05:30 offset (India has no DST), plus `IST_TIME_ZONE`: the single origin for where a day starts. "Due today", "overdue", calendar-cell assignment and day counts across the whole product resolve here, never from the server's locale or the viewer's device. `packages/domain/src/ist-day.ts`
- ⚙️ **IST instant rendering & clock skew** — `formatIstInstant(instant)` is the ONE way the product prints an absolute instant to a person (`'21 Aug 2026, 00:00 IST'`). Its day comes from `istDayOf`, so a printed timestamp can never disagree with the calendar cell the same instant lands in; it does constant-offset arithmetic with no `Intl` and no date library, because Hermes on mobile does not reliably ship a timezone database and a silent fallback to the device's zone would be the offline copy disagreeing about when things happened. Anything that is not a well-formed, real ISO instant travels back verbatim rather than as an invented time: unparseable, year-extended, calendar-impossible (`2026-02-30`), a day claim like `2026-08-20` that `Date.parse` would call midnight UTC, or a string with no stated offset that would otherwise be read in the device timezone. `IST_CLOCK_NOTE` is the line a surface puts beside a time so a collaborator in another timezone knows which clock they are reading. Beside them, `clockSkewMs` / `GROSS_CLOCK_SKEW_MS` (10 min) / `hasGrossClockSkew` compute skew from the two clocks the envelope already keeps: DERIVED, never stored and never projected, so the flag is identical wherever it is computed and an unparseable client claim counts as gross rather than as zero. `packages/domain/src/clock-skew.ts`
- ⚙️ **Plain-text document rendering** — `docToPlainText(doc: unknown): string`, a dependency-free ProseMirror/Tiptap JSON walker (coordination amendment 12): total on junk input, mention nodes `{type:'mention', attrs:{userId, label?}}` render as `@label` falling back to `@userId`, image/attachment nodes render as nothing. Pulled forward as pre-work (Plan 5 Task 1) because `proj_search` (Plan 5), Plan 7's editor, and Plan 9's notifications all consume it; landed here in §3 pending Plan 5's own catalogue task, which may relocate this bullet to §7. `packages/domain/src/doc-text.ts`
- ⚙️ **Design tokens — the one colour origin** — `primitives` (hex palette) resolved into 26 semantic `TOKEN_ROLES` for light AND dark, emitted as `--gn-*` CSS custom properties (`themeStylesheet()`: light default, dark by explicit `data-theme="dark"` or by OS preference when unchosen). The origin declares its own `CONTRAST_PAIRS` and the suite verifies all 7 pairs in both themes — a palette edit that breaks readability fails the build. Coordination amendment 11; no colour literal is legal anywhere else in any client package. `packages/ui/src/tokens.ts`
- ⚙️ **Token-discipline scanner** — walks every client source tree (present and future — trees that do not exist yet are skipped, so a new client package is covered with no edit) for hex, `rgb()`/`rgba()`, `hsl()`/`hsla()`, `oklch()`/`oklab()` and `color-mix()` literals, exempting only `tokens.ts`. Proven against planted defects before the clean-tree assertion is trusted; it does NOT detect bare CSS colour keywords (`red`, `tomato`). `packages/ui/test/helpers/colour-scan.ts`
- ⚙️ **Base UI components** — Button, Chip, Card, Avatar, Dialog, Sheet, Table: BEM class names, colour only via `var(--gn-*)`, `type="button"` by default so forms are never submitted by accident, Escape-and-scrim close on the modal pair, and horizontal scroll contained inside the table wrapper rather than the page. `packages/ui/src/components/`, `packages/ui/src/ui.css`
- ⚙️ **Client `DataSource` contract & view types** — coordination amendment 10 pinned as code: `DataSource` (`ingest`, a typed `query` surface mirroring the server reads, `subscribe(workspaceId, afterSeq, cb)`), the `StreamItem` frames (amendments 13 + 19), and the view types every client renders from (`BoardView`, `ListRow`, `TicketRead`, `AttentionItem`, `UserPreferences`, …). Views consume only this interface and never import HTTP code. Scaffold only — the online HTTP + WebSocket source and the offline replica implement these same signatures later. `packages/app-core/src/`
- ⚙️ **Client submit factory** — `makeSubmittedFactory({actorId, origin, now?})`, the one door every claim the web client makes leaves through. It mints nothing itself: the ULID and the `clientTime` stamp come from the domain's `newSubmittedEvent`, so the web client, the desktop client and the offline replica cannot grow three ideas of what a claim is; the factory adds only the per-session half (who is signed in, which origin, which clock), and `serverTime`/`seq` stay absent by construction. Proven equal, field for field, to the domain builder's own output, and proven to mint claims the envelope door admits. `packages/app-core/src/submit.ts`
- ⚙️ **Provenance rendering** — `actorLabel`, `formatDate`, `formatDateTime`, `formatStateProvenance`: honesty contract 1 as code. A missing display name falls back to the raw actor id — never blank, never a fabricated "system". Every instant is rendered by the domain's one `formatIstInstant`, never by the device: the suite renders the same claim from `Pacific/Kiritimati` and `Pacific/Niue` and demands both the same words AND the IST words, so a formatter that is merely consistently wrong fails too. A day claim (`2026-08-30`) is shown as the day it already is rather than shifted through a zone it never had, an unparseable claim renders verbatim, and a calendar-impossible day claim renders verbatim rather than throwing at a rendering surface — the plan's unguarded `istDayBounds` call would have thrown on `2026-02-30`. The unfold text reads the SERVER clock, so no claimed clock can move a ticket onto a day it was never marked on. `packages/app-core/src/provenance.ts`
- ⚙️ **Pre-check state cache** — `ClientStateCache` / `createClientStateCache()`, a snapshot of what this client has SEEN, existing only to fuel the local rule-engine pre-check. It is never rendered as truth: `withCacheFeed(source, cache)` decorates a `DataSource` so ordinary `getTicket`/`getWorkflowDef` reads FEED it and stream frames invalidate it, and nothing is ever SERVED from it — a cache hit that short-circuited a read would put a snapshot on screen as a fact. Any stream event touching an entity DROPS the snapshot rather than patching it optimistically. Its one non-obvious member is `markChildrenComplete(parentId, children)` / `hasCompleteChildren`: `childrenOf` can only answer "the children I have seen", the parent-terminal invariant needs "all of them", and a partial child set reads to the rule engine as a parent with nothing open under it. Any ticket event voids EVERY vouch — targeted invalidation would leave a vouched-but-emptied child set behind, which is the pre-check's one route to a false pass. Nothing feeds a vouch yet; until a producer does (Plan 6 Task 7 or the board/list reads), moves into terminal states answer not-evaluated rather than passed. `packages/app-core/src/cache.ts`, `packages/app-core/src/cache-feed.ts`
- ⚙️ **Local pre-check** — `precheckEvent(submitted, cache, deps?)` runs the REAL `@gisik-nokma/rule-engine` in the browser build (spec honesty contract 2) for instant, named-reason refusal previews, plus `PARENT_TERMINAL_RULE` (`hierarchy.parent-terminal`) for the owner's reopen moment on `ticket.created`/`ticket.reparented`, read through the same registered payload schemas the server's door uses rather than a cast. It is advisory: the server stays the authority. The line it holds is that a `passed` is never manufactured out of ABSENCE — four gates downgrade to `not-evaluated` instead, each closing a way the cache's silence would otherwise read as a fact: an uncached ticket or definition; an unwalkable workflow-version chain at EITHER end (a missing intermediate both invents `stranded-state` refusals and silently disarms four-eyes, which skips entries it cannot resolve; a cached definition OLDER than the version the ticket's own snapshot names makes the forward fold a no-op, so the state resolves cleanly against the wrong vocabulary and the client evaluates the pre-publish rules the server has already replaced); an accept into a terminal state with no vouched-complete child set; and — since Plan 3 landed `ticket.created`/`ticket.reparented` as engine cases — a hierarchy claim of either type, entirely, because every engine accept for them is decided behind a ticket-type definition and this cache holds none. What survives for those two is the `hierarchy.parent-terminal` refusal, which reads only cached, server-served state. A roles-bearing `restrict-to` refusal downgrades too — memberships live server-side — while an assignee-only one stands, because the snapshot holds the assignee. `completeForPrecheck` stamps `seq: 0`, a position the ledger cannot hold, so the stand-in envelope is refused by the very door it would have to pass to become a fact. The standing canary that asserted the shared engine had no case for `ticket.created`/`ticket.reparented` FIRED on Plan 3 Chain A's landing (2026-08-31), which is what it was for; it is superseded in place by one aimed at the next drift — that the engine reaches a ticket-type door this cache cannot answer, pinned in both directions so it goes red whether the dispatcher cases are removed or the adapter starts answering `null`. `packages/app-core/src/precheck.ts`
- ⚙️ **Live query hook** — `useLiveQuery(source, workspaceId, queryKey, load, debounceMs = 200)`, the refetch loop every view hook in the web client rides on: load once, then re-run `load` (debounced) on every `event`/`purge` frame the workspace stream delivers. `queryKey` names WHAT is being asked for (the project id, for a board): a changed key clears the previous answer and re-asks, and an answer that arrives for a key already left is dropped rather than rendered. The clear is a passive effect, so the window in which the previous project's data sits under the new project's heading is bounded to the single render between commit and effect rather than lasting the whole load — shortened, not removed. The key drives the reload and the WORKSPACE drives the subscription — two effects, so a key change never re-opens the stream (`subscribe` resumes from cursor `0`, and each re-open would replay the workspace from the start). Deliberately refetch-based rather than patch-based — the stream is an invalidation signal and the server projections stay the one source of rendered truth; folding raw events into rendered state is Plan 10's replica, built on reducers. Speaks only to `DataSource`, never to a URL or a socket. `packages/app-core/src/views/use-live-query.ts`
- ⚙️ **Derived progress text** — `formatRollup(rollup)` renders `"5 of 8 done · 2 restricted"`. Counts are over ALL direct children with no visibility filtering: the denominator never shrinks to what the viewer can see, and children the viewer cannot see are NAMED in the restricted count rather than pretended absent (spec §6, invariant 5). `packages/app-core/src/views/rollup-text.ts`
- ⚙️ **Board view** — `Board` + `useBoard(source, workspaceId, projectId)`. Columns are exactly the attached workflow's states, empty ones included and blocked ones marked; a project whose ticket types sit on different workflows gets one group per workflow rather than a merged column set that would invent columns no definition declares. Grouping is a rearrangement and never a filter — the same tickets grouped two ways render the same tickets, and each column's count badge agrees with the cards under it. Cards fold their state behind "who · when" and unfold to `"marked Doing by Anselma Marak on 19 Aug 2026"`, falling back to the raw actor id when a claim carries no display name; a reopen renders its `cause` as "reopened — live work added" instead of an anonymous flip; a claim still in flight to the server carries a "claim in transit" chip, which is a CLIENT-SIDE `BoardCard` flag and not a fourth `IngestResult` status. Every instant goes through the domain's one `formatIstInstant`, proven from two absurd zones by tests that hand the worker back exactly the `TZ` they borrowed. Pointing the hook at another project re-asks rather than re-rendering the last one. A test guard holds that no view module imports anything but react, the shared packages and its own relatives, and calls no network API — reading `from`, bare, dynamic and `require` specifiers, matching on whole package names rather than prefixes, and walking `src/views/` recursively. `packages/app-core/src/views/board.tsx`, `packages/ui/src/ui.css`
- ⚙️ **The ONE local storage interface** — `SyncStorage` (`run`, `all`, `transaction`, `close`) over `SqlValue`/`SqlRow`, the single seam every offline replica writes through (coordination amendment 17): better-sqlite3 answers those four methods today, in tests and the dual-client harness; it is the seam op-sqlite (React Native, Plan 10 Task 16) and tauri-plugin-sql (desktop, Task 17) will answer, and neither exists yet, and `storageConformanceTests(name, make)` is the shared Vitest suite that keeps them honest — DDL/DML round-trip, commit-and-rollback, and no interleaving of concurrent transactions. JSON travels as TEXT: the replica owns (de)serialisation so adapters stay dumb. The native engine and the conformance suite ship behind the package's `./testing` subpath ONLY; the root barrel names its five exports one by one and a standing guard walks the module graph from it, so a Tauri or Expo bundle can never be handed a node-gyp addon or a test framework by the entry point. `packages/sync-client/src/storage/`, guard in `packages/sync-client/test/barrel.test.ts`
- ⚙️ **Local replica schema** — `migrateLocal(storage)` and `LOCAL_SCHEMA_VERSION`, idempotent DDL for the eight replica tables: `events` (the visibility-scoped local ledger, keeping BOTH `seq` for entity replay and `workspace_seq` for the resume cursor, because dropping either forces the replica to invent an order it was never told), `snapshots`, the reducer-folded read models `tickets` / `workflows` / `ticket_types`, `contests`, the ordered `outbox`, and `meta`. The read models are folded locally by the domain reducer — they are NEVER a downloaded copy of the server's `proj_*` projections. `client_time` / `server_time` hold the server's Z-normalised ISO instants verbatim, so string order IS chronological order and a device-offset label must never be written there. No column carries a hand-written ULID CHECK: `ULID_REGEX` in `@gisik-nokma/domain` stays the one definition of that format, and a second one in SQL would drift. Table shapes only — snapshot policy and bounded replay belong to later Plan 10 tasks. `packages/sync-client/src/storage/schema.ts`
- ⚙️ **Rule-engine boundary** — `evaluateEvent(env, ctx)` returning Accept or a Refusal that names its rule; pass-through internals that Plan 2 replaces. `packages/rule-engine/`
- ✅ **Event ingest API** — `POST /v1/events` batch ingest: parse at the door → advisory-locked per-entity `seq` and per-workspace `workspace_seq` (workspace lock first, then entity) + `serverTime` → entity↔workspace guard → permission gate (client door only) → rule-engine gate → append + projections in one transaction → index-aligned per-event committed/invalid/refused results. `GET /healthz`. `apps/server/src/routes/events.ts`, `apps/server/src/ingest/`
  - ✅ **Envelope-origin gate (partial permission gate)** — the ingest service has two entry points, and which one a caller uses is the whole design: `ingestClientBatch` is the client door and refuses any event whose envelope `origin` is `'server'` (rule `permission.role`, reason `Only the server itself may record server-origin events.`), while `ingestBatch` is the internal door and is not gated, because the server's own appends are legitimately server-origin. **Envelope-origin is the provenance enum `'web' | 'mobile' | 'desktop' | 'server'`, NOT the browser `Origin` header — nothing here concerns CSRF.** Closes the forgery that let a client wear the server's provenance to walk past `contest.server-only` and write a permanent, un-deletable `claim.contested` attributing a fabricated claim to any actor in any workspace. Applied inside the ingest transaction (coordination decision 15), so Plan 10's `POST /v1/sync` inherits it by calling the client door. Deliberately partial and it names its own absences: no actor-identity, role, membership or visibility check yet — Task 5 fills those in on top. Landed here in §3 pending Plan 4's own catalogue task, which may relocate this bullet to §6 — Features.md has no §6 yet, and minting one early would break the mirror `test-cases/` keeps with these sections, which is why the case for it is 3.31 in `test-cases/03-foundation-ledger.md` rather than a new bucket. `apps/server/src/permissions/check-permission.ts`, `apps/server/src/ingest/ingest-service.ts`
  - ⚙️ **Error surface** — schema refusals reach the client verbatim, naming the exact rule that fired; an unexpected failure answers one fixed 500 body and never an exception message, so no SQL fragment, constraint or table name leaves through the product's only door. `apps/server/src/app.ts`
- ⚙️ **Append-only ledger** — Postgres `events` table where UPDATE/DELETE/TRUNCATE are refused by trigger, `(entity_kind, entity_id, seq)` is unique, and both clocks are `timestamptz` absolute instants: `client_time` the claimed instant beside `server_time` the received one, so they sort and compare without a cast and one moment stated in two offsets is one moment; `snapshots` table ready to bound future replay. `apps/server/migrations/`
- ⚙️ **Asia/Kolkata everywhere** — every pooled connection, the dev Postgres server, and every test database run with session timezone `Asia/Kolkata`, so an ad-hoc query reads the same clock the product shows. `apps/server/src/db.ts`, `docker-compose.yml`, `apps/server/test/helpers/db.ts`
- ⚙️ **Workspace stream cursor** — `workspace_seq`, unique per `(workspace_id, workspace_seq)` and assigned in the ingest transaction under a per-workspace advisory lock, is the only order a workspace stream may resume by; per-entity `seq` keeps entity history, replay and snapshots. Server-enriched and opaque to clients (coordination §18). `apps/server/src/ledger/event-store.ts`
- ⚙️ **Workspace stream cursor read** — `readStreamSeq(db, workspaceId)` returns the workspace's high-water `events.workspace_seq` (`0` for an empty workspace): the one position bootstrap, `subscribe.afterSeq` and `caught-up` all resume by (coordination §18). Deliberately not the envelope's per-entity `seq`, which restarts at 1 for every new entity and so silently skips their early events when used as a workspace cursor. Safe as a high-water read because ingest assigns the cursor under `lockWorkspace` inside the appending transaction. `apps/server/src/sync/stream-seq.ts`
- ⚙️ **Projection framework** — registry of deterministic `apply`/`reset` read models applied in the ingest transaction; `rebuildProjection` replays the canonical order; reference projection `proj_entity_heads` (newest event per entity, replay-safe). `apps/server/src/projections/`
- ⚙️ **Broadcast hook** — `onEventCommitted(cb)` fires only after commit, never for refused or invalid events; Plan 5 attaches WebSocket fan-out. `apps/server/src/ingest/ingest-service.ts`
- ⚙️ **Projection verifier** — `verify-projections` CLI re-derives every projection into a shadow schema, diffs against live in both directions, names drifted rows, exits nonzero on drift. `apps/server/src/tools/verify-projections.ts`

- ⚙️ **Environment contract & gate** — `.env.example` documents every configuration variable the product reads; each section names the plan that READS its group, and a variable whose plan has not landed is marked as documented ahead of its reader, not live, so an operator is never told to configure something inert without being told so. `pnpm check:env`, a step of the CI `gate` job, fails naming any variable code reads that the file does not document. The checker recognises three shapes rather than the one the plan specified: `process.env.NAME` access, destructuring off the environment, and — because this server hands the whole environment to `loadConfig` and declares its contract as zod schema KEYS — UPPER_SNAKE object keys inside files that mention `process.env`/`ProcessEnv`, which today is the ONLY shape the shipped code uses. A `process.env`-only gate would have reported “0 referenced in code” and passed vacuously forever, so two guards keep this one honest: finding zero variables anywhere is itself a failure, and so is `apps/server/src/config.ts` contributing none. `.env.example`, `scripts/check-env-example.mjs`, `.github/workflows/ci.yml`
- ⚙️ **Task ledger & drift gate** — `docs/lanes/task-ledger.tsv` carries one row per `### Task N:` heading across the eleven implementation plans (177 today), and `pnpm check:tasks` validates it. The denominator is re-derived from the plan files on every run and is never hand-typed: before this, task-level completion was tracked nowhere — only step counts were — so progress was reconstructed each session from whatever prose was nearest, and both 167 and 177 had been recorded as "the total". Status is hand-asserted and machine-validated, never inferred from commit or PR titles (four incompatible formats appear in the merged set, and this repo has already recorded commit messages as an unreliable completion signal). `done` requires the PR's MERGE commit — not the implementing commit, which a squash-merge leaves unreachable from `main` — to be an ancestor of `origin/main`; `claimed` marks completion asserted only at plan or branch granularity, counted separately and never as complete, so the honest split between verified and inherited progress is visible on the face of the report. The gate fails on a plan task with no row, a row naming a task no plan contains, a duplicate row, an unknown status, a `done` row with no evidence, and evidence not reachable from `origin/main`; it also lists merged PRs no row cites, the direction that catches implementation work landing unrecorded. Its denominator carries a positive control — every numbered plan must yield at least one task, the coordination doc exactly zero — because the instrument that first counted these headings returned BLANK, not 0, for two plans with very long lines, and a tracker whose denominator can silently reach zero reports 0/0 = clean forever. `docs/lanes/task-ledger.tsv`, `scripts/check-task-ledger.mjs`

## 4. Workflow engine & rule vocabulary

- ⚙️ **Workflow vocabulary** — workflow definitions as data: states with open/active/terminal categories, transitions (including from-any), and the closed five-rule vocabulary (restrict-to, require-comment, require-evidence, require-field, require-different-user) as zod schemas; `workflow.defined` payloads carry the full definition plus an optional stateMapping. Also the one forward state-id walk, `foldStateIdForward` — pure, and in domain because the engine, the server's ticket projection and the offline replica must all fold identically. `packages/domain/src/workflow.ts`
- ⚙️ **Structural validation** — `validateWorkflowDef`, pure and I/O-free so the future builder UI shares it: eleven plain-language checks covering workflows that cannot finish, states that cannot be reached or entered, duplicate ids/edges, and rules that can never fire or be satisfied — including `rdu-unenterable-state`, a four-eyes rule watching a state nothing in this version enters. `packages/domain/src/validate-workflow.ts`
- ⚙️ **Advisory tier** — `adviseWorkflowDef`, a separate function returning warnings the builder shows without blocking publish; the rule engine never calls it, because everything `validateWorkflowDef` returns becomes a refusal. Two codes, answering two different questions. `rdu-bypassable` names a four-eyes rule whose guarded move is reachable without ever entering the watched state. `rule-bypassable` names a rule of ANY of the five kinds — restrict-to, require-comment, require-evidence, require-field and require-different-user alike — guarding one edge into a state while another edge enters that same state carrying no rule of that kind; the from-any edge is the archetype, and a plain fast-track edge voids a guard exactly as thoroughly. A covering guard on the other edge silences it, cover being same-kind-present rather than rule-set equivalence — parameters are never compared, which is what lets the owner's sanctioned fix (the anywhere arrow carrying its own guard) actually clear the warning. `packages/domain/src/advise-workflow.ts`
- ⚙️ **Rule engine** — the real `evaluateEvent`: `ticket.transitioned` checked against authoritative state (transition legality, version walks across stateMappings, the parent-terminal-with-open-children invariant that no author can switch off, transition rules in order with first-refusal-wins); `workflow.defined` checked for structure, consecutive versioning, and stranding. `require-different-user` skips transition-log entries belonging to a workflow the ticket has been migrated off and resolves the rest forward through the version chain before comparing, so neither dropping and remapping a state nor a workflow migration can disarm four-eyes. It reads the log in ascending `seq` — the ordering is established at the point of use rather than inherited from whichever projection appended the entries — and it fails CLOSED: an entry it cannot resolve forward refuses the move ("this ticket's history cannot be read against its current workflow") instead of being skipped, because a history that cannot be read is not the same answer as a history with nobody in it. Every refusal names its rule and reasons in plain language. `packages/rule-engine/src/`
- ⚙️ **Contest evaluators** — the rule half of the contest lifecycle, run by the same shared engine on server and client. `claim.contested` is refused `contest.server-only` unless it arrives with `origin: 'server'`: a contest is the system's own record of a refusal, and a client that could forge one could forge its own exoneration. `claim.contested_resolved` is refused `contest.unknown` when it names no recorded contest, `contest.wrong-ticket` when the contest it names sits on a different ticket, and `contest.already-resolved` on a second resolution, because settling a settled contest would rewrite history. There is deliberately NO role gate on resolution — restricting it to the claimant or to an admin would leave contests rotting on tickets whose own collaborators could settle them, and the resolution is itself a recorded, attributed event. The lookup joins `EngineContext` as an OPTIONAL `getContest`, so every context predating contests still typechecks; a context that cannot answer it makes the evaluator THROW rather than refuse, because a wiring bug is not a claim about the world — without that guard the same missing lookup degrades into a `contest.unknown` refusal that reads entirely legitimate. Rule ids are dotted where `REFUSAL_RULES` are bare, deliberately: a rule id is an opaque string compared character for character by fixtures, the server's error surface and both clients. `packages/rule-engine/src/contests.ts`
- ⚙️ **Planted-defect fixture suite** — 84 JSON fixtures, one per refusal path plus accepting twins, run by an in-memory harness and exported so server and client builds prove the same refusals against the same defects. The harness prior-event schemas mirror their domain twins in PRESENCE and deliberately not in VALUE FORMAT: a fixture may use `t1` and `ws_1` because a prior event never passes `parseEvent`'s door, but it may not omit a key the real door requires — a looser prior door stages a world the server could never have produced, and the suite then proves a refusal against history that cannot exist. Each may carry an optional `notes` string — the only comment JSON allows — for a fixture whose shape is load-bearing beyond the outcome it asserts. The harness completes every prior event BEFORE filtering contest events out of the ticket-state fold, and the order is load-bearing rather than stylistic: default event ids are `fx_evt_<seq>` derived from POSITION, so filtering first REMOVES the contests before they are ever given ids — and a two-list variant that keeps them RENUMBERS the survivors instead. Either way a fixture naming `fx_evt_1` addresses nothing, and a double resolution refuses `contest.unknown` where it meant `contest.already-resolved`: still refused, wrong rule. The filter itself is mandatory, not hygiene: the fold throws on any type it does not know. `packages/rule-engine/fixtures/`, `packages/rule-engine/src/fixtures/harness.ts`
- ⚙️ **Workflow projection** — `proj_workflows` keeps every published version queryable (the engine's version walk needs intermediates and their mappings) and backs the server's `getWorkflowDef`; each row records the ledger position it was published at, so a definition can be asked for as of a point in the ledger rather than only as of now; idempotent apply, deterministic rebuild. `apps/server/src/projections/workflows.ts`
- ⚙️ **Type↔kind binding at the door (G1)** — `workflow.defined`'s registration declares `entityKind: 'workflow'`; `parseEvent` refuses any envelope naming that type against a different entity kind (`entity-kind-mismatch`), the same general door every entity-kind-declaring registration gets (coordination doc §11). Layered with the engine's own kind checks by design: fixtures and Plan 10's offline replica reach `evaluateEvent` directly, bypassing `parseEvent`, so the door alone would leave them unguarded. `packages/domain/src/parse-event.ts`, `packages/domain/src/registry.ts`
- ⚙️ **Entity↔workspace binding at ingest (G2)** — an entity belongs to one workspace forever: `commitOne` reads `proj_entity_heads` after both locks and before the engine runs, and refuses `entity-workspace-mismatch` when an envelope's `workspaceId` disagrees with the entity's recorded one. A server-side door, deliberately not a shared-engine rule — a workspace-scoped client replica cannot see that an entity id is already bound elsewhere, so Plan 10's offline replica must mirror this door knowingly rather than find it in the fixtures. No fixture; proven by integration test. `apps/server/src/ingest/ingest-service.ts`
- ⚙️ **Projection registration order, pinned (G3)** — `buildProjectionRegistry()` registers `proj_entity_heads` before `proj_workflows`; registration order is application order inside the ingest transaction (coordination doc §8), so a projection may read a table an earlier one wrote in the same transaction. A DB-free test pins the exact array, so a re-ordering breaks loudly rather than silently before any later projection comes to depend on it. `apps/server/src/projections/index.ts`

## 5. Tickets, hierarchy & rollups

*(Plan 3's keystone only — the ticket type model, the event vocabulary, and the engine-context rider that had to ship with them. The reducer, hierarchy and field refusals, the three projections, the rollups and the history endpoint arrive with the rest of Plan 3's lane and extend this section.)*

- ⚙️ **Ticket type system** — built-in ladder epic(1)/story(2)/task(3)/sub-task(4) as seed data plus custom reusable types defined by `ticket-type.defined` events: name, icon, rank, workflow binding, and typed custom fields (text, number, date, select, person), Zod-validated. A select field cannot exist without its choices, no custom field may shadow a built-in id, and `DEEPEST_RANK` is a pinned constant rather than a maximum over the defined types — the rank at or below which a type's tickets will require a parent must not shift underfoot when an admin defines a deeper type. `packages/domain/src/ticket-types.ts`
- ⚙️ **Ticket event vocabulary** — eleven registered types, all v1, each bound to the entity kind it is about: `ticket-type.defined`, `ticket.created` (whose `title` must not be blank — `.min(1)` alone admitted `'   '`, which titles nothing while looking like a title everywhere it is displayed, and which the edit door already refused, so the create door was admitting precisely the state the edit door forbids; it REFUSES rather than trims, as the workspace and project names do, and a padded real title is stored verbatim), `ticket.transitioned` (Plan 2's shipped payload, whose optional `cause` marks a reopen forced by arriving live work), `ticket.assigned`, `ticket.collaborator_added/removed`, `ticket.field_set` (built-ins title/description/dueDate/startDate ride it; a due date and a start date are always `{date, note?}` claims, and `value` must be PRESENT — `z.unknown()` alone left the key optional, and the reducer's then-`?? null` folded an omitted value into a clearing claim nobody made; with the key required that coalesce was unreachable and has been dropped, because keeping it would state the defect as the design), `ticket.reparented`, `ticket.workflow_rebound`, `comment.added` (opaque doc body), `attachment.added` (a `kind`-discriminated union: an `upload` carrying the server's sniffed mime/size and its `sha256` of the stored bytes, or a `drive-reference` carrying the pointer plus the name, mimeType and `capturedAt` last seen on a file this product does not hold). Unknown types, malformed payloads and misfiled entity kinds are refused at the door. `packages/domain/src/events/ticket-events.ts`, `packages/domain/src/vocabulary.ts`
- ✅ **Hierarchy sanity refusals on creation** — `checkTicketCreated` forces every precondition creation has *in this plan*, in a deliberate order, each in plain language: the ticket must not already exist, its type and that type's workflow must be defined, a type at or below `DEEPEST_RANK` must name a parent, and a named parent must exist in this workspace, sit in the same project, have a readable type, outrank the child, and not already be finished. The order is load-bearing and tested as its own property — the most fundamental truth names the refusal, and the one remedy that is an *offer* (reopen the finished parent) comes last so it is never offered while something else is still in the way. Two refusals exist because a borrowed sentence was false on the path that reached it: `hierarchy.parent-type-unknown` (the ticket's own type had already resolved) and `hierarchy.unknown-parent` for a parent in another workspace (ticket lookup is global, so a foreign parent resolves — and naming its project would both lie and confirm the id exists). - ✅ **Hierarchy sanity refusals on reparenting** — `checkTicketReparented` asks creation's questions of a ticket that already exists, plus the one creation cannot raise: a **loop**. Order: unknown ticket → unknown type → (to project root) the deepest-rank rule → self/cycle → unknown parent (a parent in another workspace is one of these) → cycle by ancestry → cross-project → parent's type unknown → rank → parent-terminal, and a loop is named as a **loop** even when rank or project is also violated. The cycle walk is not dead code under strict rank ordering: `ticket-type.defined` is last-definition-wins, so a workspace can move a type's rank *under* one it already contains, after which a loop-closing reparent is rank-legal and nothing else refuses it. A parent chain that never ends throws rather than refusing — a cycle already standing in the tree is the store's state, not a claim the actor can be told anything true about. `packages/rule-engine/src/checks/hierarchy.ts`
- ✅ **Workflow migration checks** — `checkTicketWorkflowRebound` guards `ticket.workflow_rebound`, the deliberate, attributed act that moves an existing ticket between two unrelated workflows (a ticket otherwise pins the workflow it was created under, so re-pointing a *type* changes only what new tickets get). A rebound to the ticket's **own** workflow is refused, and that is the load-bearing one: the event sets `stateId` directly and evaluates no transition rule, so permitting it inside one workflow would let any actor who can emit it reach any state without satisfying `restrict-to`, `require-comment`, `require-evidence`, `require-field` or `require-different-user`, and without leaving the log entry four-eyes reads. An undefined target workflow and a state the target does not have are refused too — the ledger accepts only what it can later replay — and each names its own subject: `ticket.rebound-unknown-workflow` names the workflow the *payload* asked for, never the ticket type's binding, which on a migration may be perfectly well defined and is beside the point (controller ruling P13). - ✅ **Field claim checks** — `checkTicketFieldSet` guards `ticket.field_set`, the one event that carries every field claim a ticket has. The four built-ins are answered BEFORE the ticket's type is resolved, because they belong to no type and refusing a rename with "this ticket's type is not defined" would name the wrong noun. `dueDate` and `startDate` share one branch and one schema rather than two that could drift, and a custom `date` field is held to `IST_DAY_REGEX` — the same one origin of what a day is. `packages/rule-engine/src/checks/fields.ts`
- ✅ **Built-in rank lock, enforced at the server** — `checkTicketTypeDefined` refuses `type.builtin-rank` when a `ticket-type.defined` re-ranks one of the four built-ins. The type builder locked those ranks in the UI while last-definition-wins accepted a re-rank anyway, and a lock the server does not hold is a description of a rule: `DEEPEST_RANK` is 4 *because* the built-in sub-task's rank is, so re-ranking `sub-task` to 3 released every sub-task from the parent requirement while the builder still displayed the lock. Only the rank is locked — a built-in's name, icon, workflow binding and custom fields stay an admin's to change (which is also how built-ins are seeded per workspace), and custom types stay re-rankable in either direction. `packages/rule-engine/src/checks/ticket-type.ts`
- ✅ **Malformed-payload refusals name their field** — every check that parses a payload renders its detail through one `malformedPayloadDetail`, which mirrors `parse-event.ts` and writes `at <path>: <message>` per issue, omitting the clause where the payload failed at its root and there is no path. Before it, each of the seven call sites joined `issue.message` alone and dropped the zod path — so a `ticket.created` with two ULID fields refused a bad `parentId` with "must be a ULID", a rebound with an empty `toStateId` blamed nothing at all, and a field claim with no value produced a sentence with no noun. One helper rather than seven copies, in the module all seven already import, so the next check that parses a payload reaches for it instead of copying the fragment. `packages/rule-engine/src/refusal-rules.ts`
- ⚙️ **Honest engine-context seam** — `getEntityState` answers `null` for the kinds this server cannot yet serve ('ticket' until Plan 3's projections; 'membership' still, even though Plan 4's `proj_memberships` has now landed — **no task in Plan 4 owns the wiring**, ruling P18, so `restrict-to`'s role criterion goes on refusing on the server path) and returns the whole state, `{kind, id}`, for the four kinds whose state is exactly that. The plan text's handler resolved only the new ticket ("a fresh ticket has no children"), which is true of arrival order and false of replay — a grandchild would have been left at the project default while live said otherwise, and `verify-projections` would have reported drift on a table nobody corrupted. So `ticket.created` re-resolves a subtree too, and `visibility.set` is keyed on **`event.entity.id`, never `payload.ticketId`**, so no ticket's stream can write another ticket's row before Task 9 exists to refuse the disagreement. `apps/server/src/projections/proj-visibility.ts`, `apps/server/test/proj-visibility.test.ts`
- ⚙️ **`canSee` — the one visibility decision** — `canSeeResolved(eff, userId, resolved)` is a pure function of the viewer's effective role and the ticket's resolved audience, and it is the whole decision: a **non-member** sees nothing; a **guest** sees only explicit lists that name them (never workspace or project modes, and never through a project attachment — the guest branch does not consult the project set at all); a **member or admin** sees workspace mode always, project mode only from inside the project, explicit mode only when listed; the **owner** sees everything in the workspace. Admins get **no read bypass** — an admin joins a project, an attributed event, and reads afterwards — and the project-admin flag is management, not reading. Nothing here reads a clock, a locale or a random source. `apps/server/src/visibility/can-see.ts`
- ⚙️ **`canSee` reads membership through `resolveEffectiveRole`, and the workspace it asks about is the TICKET's** — never a direct project-scope `SELECT` on `proj_memberships`: a revocation deletes only the workspace-scope row, so a project-scope row **survives** and a bare read returns rows for people no longer in the workspace. `canSee` also takes no `workspaceId` parameter — it resolves the role in the workspace the ticket's own row names, so a role held in one workspace answers nothing about another's ticket. A ticket with no `proj_visibility` row answers `false`, identically to one the viewer may not see. `apps/server/src/visibility/can-see.ts`
- ⚙️ **`listVisibleTickets` — the same table as one SQL predicate** — a viewer's whole slice of a workspace in one round trip rather than N. It is the decision table **said twice**, which is the two-sources-of-truth shape this series keeps catching, so the cost is paid by a test rather than a comment: every viewer class in one fixture is asserted both against its exact expected id set and against `canSee` ticket by ticket, with a non-vacuity assertion so the agreement cannot be agreement about two empty answers. It returns `proj_visibility` rows today — **`proj_tickets` does not exist on this branch** (Plan 3 Task 12 owns it) and no competing definition of it is invented here; the join lands with that table, behind the same WHERE clause and the same tests. `apps/server/src/visibility/visible-tickets.ts`
- ✅ **Reads enforce visibility, and an invisible ticket is indistinguishable from one that never existed** — `GET /v1/workspaces/:workspaceId/tickets`, `.../tickets/:ticketId` and `.../tickets/:ticketId/events`, all three behind `requireSession` and all three deferring every audience question to `canSee`. A direct read of a ticket the viewer may not see answers `404 {error:'not_found'}` with the **same status, body and headers** as a read of an id that never existed, so a member probing another project's ids learns nothing; the history door is refused identically, because it is a separate registration that would otherwise have to be refused separately. On the collection the same rule runs the other way: an outsider gets `200 { tickets: [] }`, never a refusal, since an empty/non-empty distinction would be the oracle the 404 discipline removes. The route adds exactly ONE question of its own — is this ticket in the workspace the path names — which is identity, not audience: `canSee` deliberately takes no workspace, so without it a member of two workspaces would read B's ticket through an A-shaped URL. `apps/server/src/routes/tickets.ts`
- ✅ **The restricted-parent placeholder, and the existence it must NOT invent** — a visible child under a parent it may not see returns `parent: { kind: 'restricted', id }`: existence and id, structurally unable to carry more, so the child never poses as parentless. That is the one deliberate existence leak in the product (spec §6), reachable only through a child the viewer can already see. Its inverse is closed in the same branch: `canSee` answers `false` alike for an invisible ticket and for one with **no row at all**, so collapsing the two would assert the existence of a ticket nothing has evidence for — a `parent_id` naming no ticket returns `parent: null`, the same answer `proj_visibility` gave when it resolved that child as a root. Rows are `proj_visibility`'s and there are **no ticket titles anywhere queryable** on this branch, so the placeholder ships as existence-versus-the-row rather than existence-versus-title, recorded rather than papered over. `apps/server/src/routes/tickets.ts`
- ✅ **A served row goes out through an allow-list, because one of `proj_visibility`'s columns is a ticket id** — `resolved_from` names the nearest *authored* ancestor, which is deliberately not the immediate parent, so `SELECT *` would have disclosed the existence of a ticket that is neither visible nor the parent: exactly the leak the placeholder is bounded to avoid. It is cut, along with the explicit audience rosters, in the one mapper both the list and the single read go through; `parent_id` stays, being the same fact as the placeholder itself. The **history endpoint is deliberately not trimmed the same way** — the ancestor ids in a `ticket.created` or `ticket.reparented` payload are provenance, an attributed claim, and spec §6 says provenance is never redacted. Cut derived state; never cut a claim. `apps/server/src/routes/tickets.ts`
- ✅ **Provenance is never redacted from someone entitled to the state** — ticket history is the ledger, filtered: full envelopes with `actor_id` and both clocks, unchanged even when the actor shares no membership at all with the viewer. Both instants are rendered as absolute ISO 8601 `Z` explicitly rather than left to the serializer, because the session runs in Asia/Kolkata and any other rendering would put an offset label into a field every client parses as a moment. There is deliberately **no second, anonymizing serialization path** — a redacting path that exists is a path something can drift into. `apps/server/src/routes/tickets.ts`
- ✅ **Rollup honesty — the true total, with the restriction NAMED** — the single-ticket read carries `rollup: { total, restrictedCount } | null`. `total` counts **every** direct child with no visibility filtering whatever, and the part the viewer cannot reach is disclosed beside it rather than subtracted out of it, because a rollup showing only what a viewer can see understates the work and makes a parent look complete when it is not (spec §6). The asymmetry is the design: **`total` is per-parent and `restrictedCount` is per-viewer**, so two people reading the same parent get the same total and different restrictions. There is no third `visibleCount` field: one shipped and was **removed after measurement** — mutating its counter to `total - restrictedCount` killed nothing in the whole server suite, so the invariant defending it was decoration, and the enumeration is cross-checked against `canSee` child by child instead, which is an independent witness rather than arithmetic. The viewer's role is resolved once per **distinct child workspace** — the workspace is the ticket's, never the caller's — rather than once from the first child, and a child in a foreign workspace is counted in the total rather than quietly dropped. **The per-category half is absent rather than zeroed**: "5 of 8 **done**" needs each child's `state_category`, which lives in `proj_tickets` via `proj_rollups`, and neither table exists on this branch (Plan 3 Tasks 11 and 12) — so `open`, `active` and `terminal` are left off the type entirely, since a `0` would be a lie and a `null` still invites a client to render the phrase, while an absent key makes the compiler demand a decision the day the table lands. A childless ticket answers `null`, not a zeroed family, matching what `proj_rollups` will store. `apps/server/src/visibility/rollup.ts`, `apps/server/src/routes/tickets.ts`
- ✅ **The sync-down visibility filter — what leaves the server for a device it does not control** — `visibleEventsFor(db, userId, workspaceId, afterSeq)` streams a workspace's ledger past a cursor, filtered against visibility **as of now**, and yields `LedgerEvent | PurgeInstruction | ScopeRevokedInstruction`. An event about a ticket the viewer cannot see now is never yielded — **not the payload and not the id**, because an envelope naming a ticket while withholding its body still discloses that the ticket exists, which is the oracle the read door spent a whole task closing. What a revocation inside the window took away comes back as a tombstone instead, since an event that merely stops arriving leaves the data on the device forever: a `visibility.set` or a `ticket.reparented` that moves a ticket out of view purges it **and every inheriting descendant under it**, and losing a project purges that project's now-invisible tickets. `afterSeq` is the **workspace** cursor (`workspace_seq`, coordination §18) and never a per-entity `seq` — every entity restarts its own counter at 1, so ordering the stream by it would bury the entire early history of anything born after the cursor. Membership is asked only through `resolveEffectiveRole`, never off `proj_memberships`, whose project-scope rows survive a revocation by design. The purge walk carries a **cycle guard**, which is not defensive dressing: the parent graph can contain a loop and nothing on this branch refuses one (case 6.58), and since this walk descends `parent_id` rather than ascending it, a loop is unbounded recursion inside the generator that serves every replica — a hang on a request path rather than a wrong answer. Non-ticket traffic splits by role: workspace, project and membership events go to non-guests; workflow and ticket-type definitions go to everyone, guests included, because a guest cannot render their explicitly-shared ticket's status without the workflow that names its states. `apps/server/src/visibility/visible-events-for.ts`
- ✅ **A device whose owner was put out of the workspace is told, and the plan's own code could not tell it** — the plan text opened with `if (eff.workspaceRole === null) return;` and placed the `membership.revoked` purge branch *inside* the loop below it. Those two lines cannot both run for the same person: a revocation deletes the workspace-scope row, so the revoked user's role **is** null and the generator returned before reaching the branch written to serve them. Every ticket on that replica would have stayed there. The discriminator is the **range, not the role** — a stranger's window contains no `membership.revoked` naming them, and someone revoked before the cursor was already told — so a null role plus a revocation in range yields one `{kind:'scope-revoked'}` and stops. It is necessarily scope-level: itemising would mean asking which tickets are invisible to someone invisible to everything, which returns the **whole workspace**, handed as a count to a person now standing outside it. A guest is answered the same way and for the same reason; a member still inside the workspace's accepted existence-leak gets the itemised purges. `apps/server/src/visibility/visible-events-for.ts`
- ⚙️ **Which entity kinds may travel is decided by the compiler** — `audienceClassOf` maps every `EntityKind` to one of `ticket · roster · workspace · definition · withheld` through a **bare switch with no `default`**, the idiom `canSeeResolved` established: a kind no `case` names falls out, the function ends without returning, and tsc refuses it with TS2366. Measured rather than asserted — adding a member to `ENTITY_KINDS` raises TS2366 at that function and, on this branch, **nowhere else in the server**, so it is the only place a new kind is forced to declare an audience. Without it a kind added by a later plan would be silently dropped from every replica, or — under a permissive `default` — silently sent to everyone. `invite` is classified `withheld` from **everyone**, owners included: `invite.sent` carries an email address, the owner/admin slice that should carry it is Task 13's, and shipping it to every member meanwhile would disclose the PII that slice exists to protect. `apps/server/src/visibility/visible-events-for.ts`
- ⚙️ **`EffectiveRole` is branded, so its provenance is a constraint rather than a convention** — a module-private `unique symbol` that only `effective-role.ts` can write, closing ruling P22. Every safety property proved of `canSeeResolved` rests on its `EffectiveRole` having come from `resolveEffectiveRole`, which is the only thing that makes a null workspace role imply an empty project set; TypeScript is structural, so before the brand any object of the right shape was accepted and a hand-built or stale one would have carried a project set no early return had emptied. It does not make hand-building impossible — two pure-function test helpers legitimately cast — it makes it a **deliberate, greppable assertion at a named site** instead of an accident. `apps/server/src/permissions/effective-role.ts`
- ⚙️ **Scenario seeds built from real events** — `seedMember`, `seedGuest`, `revokeMember`, `seedProject`, `seedTicket`, `setVisibilityEnv` drive the **real projections** with the **real event payloads** rather than writing the projection tables by hand. That is what makes the revoked-member case honest: the surviving project-scope row has to arrive the way a real revocation leaves it, or a test built on it would pass with the safety property deleted. `seedTicket` also appends its `ticket.created` to the **ledger**, because creatorship is read from there and a projection-only fixture would leave every creator lookup answering null. `apps/server/test/helpers/seed.ts`
- ⚙️ **Canonical simple-Kanban workflow template** — the definition a new workspace is founded on, deep-cloned per use so editing a clone can never reach the template. `packages/domain/src/simple-kanban.ts`

*(Plan 10, Task 4 only — the LIFTED §11 closer and the contested-claims read path. Plan 10's own

- ✅ **A contest cannot lie about which claim it is contesting** — `claim.contested` embeds the
  refused claim whole, and the embedded claim must name the **same workspace, the same entity kind
  and the same entity id** as the envelope carrying it. Before this, every layer validated one half
  and none compared the halves: a contest filed on a real ticket in its real workspace could embed a
  fabricated claim naming any other ticket in any other workspace, and it committed — a permanent,
  un-deletable ledger entry attributing a fabricated claim to any actor, since the ledger is
  append-only by trigger and can only ever be superseded. The check is **pure** (no database read, so
  it cannot go stale or be defeated by a missing row) and runs on **both ingest doors**, unconditionally
  — unlike the envelope-origin gate, which must distinguish doors because the server's own appends are
  legitimately server-origin. `apps/server/src/sync/contest-coherence.ts`
- ⚙️ **The server-side contest constructor** — `buildContestedClaim` reads the contest's workspace and
  entity **off the refused claim**, so it has no parameter through which they could disagree: coherence
  is structural there rather than checked. `checkContestCoherence` is the door that catches a contest
  built any other way. What neither can establish, and it is named rather than implied: that the
  embedded claim was **actually refused**, by the rule the contest names. Only the path that holds a
  real refusal can answer that — *owner: Plan 10 Task 7, `POST /v1/sync`*. `apps/server/src/sync/contest-coherence.ts`
- ⚙️ **Contested-claims projection (`proj_contested`)** — one row per `claim.contested`, keyed by the
  contest event id and UNIQUE on the refused claim's id, so a sync retry finds the prior contest
  instead of filing a second one. `claimant_id` is the actor of the **refused claim**, not of the
  contest — the server files contests, so reading the contest's own actor would name the same person on
  every row and empty My Work for everyone. `original_event_id` is deliberately **not** a foreign key
  into `events`: a refused claim is never appended, so the row it would point at does not exist.
  `apps/server/src/projections/contested.ts`
- ⚙️ **Both writers of a contest row are one ticket's stream** — `claim.contested` and
  `claim.contested_resolved` are both filed against the ticket, and the engine refuses
  `contest.wrong-ticket` for a resolution aimed elsewhere, so canonical replay
  `(entity_kind, entity_id, seq)` always puts the contest before its resolution. A resolution reaching
  the handler with no contest row throws rather than silently doing nothing — the assertion of that
  premise, not defensiveness: a silent no-op would leave a resolved contest showing as open forever
  with no instrument saying so. The cost, named rather than left to be discovered: a rebuild replays the
  whole ledger in one transaction, so one inconsistent pair means `proj_contested` cannot be rebuilt at
  all until the ledger is superseded into consistency. `apps/server/src/projections/contested.ts`
- ⚙️ **The verifier runs over `proj_contested` with a real row in it** — `original_event` is the repo's
  first `jsonb` projection column, and the registry contract forbids `json` precisely because
  `verify-projections`'s `EXCEPT` diff needs an equality operator. That jsonb has one is an argument
  about the type; that a live `INSERT` and a shadow-schema rebuild agree through it byte for byte is an
  observation, and the verifier's seed now makes it. Its non-emptiness is asserted separately, because a
  clean verdict over an empty table is the check that cannot fail.
  `apps/server/test/verify-projections.test.ts`
- ⚙️ **`getContest` on the server engine context** — the engine's contest lookup, reading
  `proj_contested` through the ingest transaction's own client, which is what makes
  `contest.unknown` / `contest.wrong-ticket` / `contest.already-resolved` evaluable on this server at
  all. `null` here means "no such contest was ever recorded", which is TRUE of a projection rebuildable
  from the whole ledger — the reason the evaluator **throws** when the method is absent and **refuses**
  when it answers null. Asserted through the ENGINE — the three contest refusals `contest.unknown`,
  `contest.wrong-ticket` and `contest.already-resolved` are the whole reason the method exists, and a
  direct call would prove the SQL runs while proving nothing about the wiring that was missing.
