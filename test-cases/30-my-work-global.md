## 30.2 Preferences (T2)

`GET`/`PUT /v1/me/my-work-preferences` — the page's "Show" filter and "Group" toggle, one document per user (`user_my_work_preferences`, keyed by `user_id` alone). All six in `apps/server/test/routes/my-work-preferences.test.ts`, built through `buildTestApp` so `app.ts`'s registration is under test; 30.013's frozen default also in `packages/domain/test/my-work-preferences.test.ts`.

- ✅ **30.013 — GET with no row answers `DEFAULT_MY_WORK_PREFERENCES`** (`{show:['created','assigned'], grouping:'workspace-project'}`), asserted as the literal and as the domain constant; the default and its `show` array are frozen (a push into `show` throws, and the default is unchanged after it; control: a parsed copy of the same doc is not frozen). Mutations: the store returns `null` for no row → red; either `Object.freeze` dropped → red.
- ✅ **30.014 — PUT a valid doc answers it, and GET answers it after, for the same user;** a second PUT replaces the first whole.
- ✅ **30.015 — user B never sees user A's doc:** B reads the default after A's PUT; control: A reads its own doc; B's own PUT then leaves A's alone. Mutation: the store keyed on a constant instead of `user_id` → red.
- ✅ **30.016 — a bad body is a 400 `invalid_my_work_preferences` and stores nothing:** `show:[]`, `show:['bogus']`, an extra key, `grouping:'tree'`, and five `show` entries (`.max(4)` bounds the raw body, before the de-dupe), each otherwise valid; for a fresh user GET still answers the default and for a user with a prior doc GET still answers that doc. Controls: a one-value doc and a four-value doc are taken. Mutations: `.min(1)` dropped, `.strict()` dropped, `.max(4)` dropped → red.
- ✅ **30.017 — anonymous GET and PUT are 401 `UNAUTHENTICATED_BODY`,** and the PUT adds no row.
- ✅ **30.018 — duplicate `show` values are stored once, first occurrence first:** `['created','created']` → `['created']` and `['assigned','created','assigned']` → `['assigned','created']`, in the PUT answer and in a later GET. Mutation: the de-dupe removed → red.

The PUT is a cookie-authenticatable per-user write, so it is in `HTTP_ORIGIN_PROTECTED_ROUTES` (`apps/server/src/http/http-origin.ts`) with its own row in `apps/server/test/http/security-middleware.test.ts` (13.116's set-equality guard), and the new table has a `not-entity-bearing` purge rule (`apps/server/src/purge/table-rules.ts`, 19.083's every-table guard).

## 30.5 MCP (T5)

`get_attention` and `my_work` in `packages/mcp-server/src/tools/discovery-tools.ts`. With no `workspaceId` both go GLOBAL: one `/v1/me/workspaces` read, archived workspaces skipped, then one read per workspace in that list's order. `get_attention` takes `show` (default `created,assigned`), narrowed per workspace by the same rule as T3's `showForWorkspace`. The global answers are `{ workspaces: [{ workspaceId, name, items }] }` (attention) and `{ workspaces: [{ workspaceId, name, groups, projectNames, stateNames }] }` (my work, each workspace's `/v1/me/work` body plus its name). Unit cases in `packages/mcp-server/test/discovery-tools.test.ts`; the hosted legs of 30.051, 30.053 and 30.055 in `apps/server/test/mcp/mcp-discovery.test.ts`.

- ✅ **30.051 — `get_attention` with no arguments reads `/v1/me/workspaces`, then each live workspace's attention route with `show=created,assigned`,** in list order, and answers `{ workspaces: [{ workspaceId, name, items }] }` (the per-workspace `settings` and `generatedAt` are not carried). Hosted: a plain member's `get_attention({})` passes the door's `inputSchema` and T1's route answers it, the member's workspace listed with its name.
- ✅ **30.052 — `get_attention({workspaceId})` is ONE call, `/v1/workspaces/w1/attention?show=created,assigned`, answered in today's shape** (the route's body unchanged). Control: an explicit `show` (`['ws-admin','created','ws-admin']`) is sent in canonical order and once each, `show=created,ws-admin`.
- ✅ **30.053 — `show` is narrowed per workspace, and a workspace with nothing left to ask is skipped, never 400ed:** `show:['ws-admin']` asks only the workspaces the caller owns or admins; `show:['project-admin']` only the one where they run a project (a row without `adminProjectIds` counts as none). Control: all four values ask the owned and the admin workspace for `created,assigned,ws-admin`, the project-run one for `created,assigned,project-admin` and the plain one for `created,assigned`. Hosted: a member's `show:['ws-admin']` answers without their workspace (T1's route would 400 it), the owner's includes it, and the member naming the workspace outright gets the route's refusal.
- ✅ **30.054 — `show:[]` and an unknown value are refused before any read** (zod: at least one value of the four), with or without a `workspaceId`. Control: `show:['created']` answers.
- ✅ **30.055 — `my_work` with no arguments reads `/v1/me/work?workspaceId=` for each live workspace** (the archived one is never read) and answers each body with its workspace's name. Hosted: a member's `my_work({})` lists their workspace with its groups.
- ✅ **30.056 — `my_work({workspaceId})` is today's single call, answered unchanged:** no workspace list is read, and an archived workspace named outright is still read.
- ✅ **30.057 — the two tool descriptions match the plan verbatim,** each saying the default covers all your workspaces and how to narrow it (`get_attention` also names `show`).
- ✅ **30.058 — one workspace answering 404 is left out and the rest return,** for both tools. Control: a 500 from one workspace fails the whole call rather than return a partial answer that looks complete.
