## Filled from Plan 4's reserved range

- **6.5** ✅ `proj_memberships` resolves effective roles. A grant records who granted it, when, and at which stream position; a re-grant updates the role in place, one row per membership identity, carrying the later event; a revocation removes the workspace row so the role stops being conferred, and touches only the revoked user; project roster events add and remove project-scope rows carrying the project-admin flag, and a project removal leaves the workspace row and other projects standing. A non-member resolves to null with no projects; the newest grant wins; a revoked member resolves to nothing **though the roster row survives in the table**; a re-grant after a revocation restores the role; a role held in another workspace does not carry over. `hasProjectAdminRights`: owners and admins hold rights on every project including ones they are not on, a project admin on that project only, a plain project member none, a guest none even on a project they are on. **The determinism case is the load-bearing one** — live application and a rebuild from the ledger agree though the two orders differ — because the plan text's revoke handler failed exactly there. (`apps/server/test/proj-memberships.test.ts`, `apps/server/test/permissions/effective-role.test.ts`)

- **6.9** ✅ Visibility resolution. - **6.10** ✅ Re-resolution, pruning, and a rebuild that reads the ledger in the order a rebuild really uses. An ancestor's visibility change reaches every inheriting descendant; re-resolution **stops dead at an authored descendant and at everything under it**; a reparent moves the ticket and its subtree onto the new chain, and to root falls back to the project default; setting a ticket back to `inherit` re-attaches it and its subtree. **The determinism cases are the load-bearing ones, and they are deliberately not the plan's** — and they hold only while the parent graph is **acyclic**, which the case title says and case 6.58 measures. The plan's own rebuild test replays the same arrival order it applied, so it asserts only that `apply` is a function; these three seed the real ledger, assert that canonical order genuinely differs from arrival order, and compare live against a **rebuild** — enumerating a child created before its parent's row exists, an authored node pruning mid-chain, and a reparent-plus-set-back-to-inherit moving a subtree.
