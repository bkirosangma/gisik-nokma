## Filled from Plan 4's reserved range

- **6.5** ✅ `proj_memberships` resolves effective roles. A grant records who granted it, when, and at which stream position; a re-grant updates the role in place, one row per membership identity, carrying the later event; a revocation removes the workspace row so the role stops being conferred, and touches only the revoked user; project roster events add and remove project-scope rows carrying the project-admin flag, and a project removal leaves the workspace row and other projects standing. A non-member resolves to null with no projects; the newest grant wins; a revoked member resolves to nothing **though the roster row survives in the table**; a re-grant after a revocation restores the role; a role held in another workspace does not carry over. `hasProjectAdminRights`: owners and admins hold rights on every project including ones they are not on, a project admin on that project only, a plain project member none, a guest none even on a project they are on. **The determinism case is the load-bearing one** — live application and a rebuild from the ledger agree though the two orders differ — because the plan text's revoke handler failed exactly there. - **6.59** ✅ **The ruling, made falsifiable — and the half of it that could not be.** A member on a project is **revoked** from the workspace; their project-scope `proj_memberships` row is still standing, and the case **selects that row and asserts its contents**, not its count, because if the row were gone then `canSee` answering `false` would prove only that a missing row confers nothing. Two guards stand on this path, and **on the ruling's own mode they are REDUNDANT, not independent** — measured one assertion at a time, which is the granularity the first write-up of this case lacked. Neutralising only `canSeeResolved`'s null short-circuit — routing a null role into the member branch, which is what deleting it did while the role was an if-chain, deleting it outright now being a TS2366 — fails `:232` (`workspaceMode`) while **`:231`, the project-mode revoked member, still passes**; deleting only `resolveEffectiveRole`'s early return fails nothing in this file; **both together** fail `:231`. So on the project-mode path either guard alone blocks the leak, and on the workspace-mode path — where no project set is consulted — only the short-circuit stands. Both are present and the code is correct; the earlier sentence claiming the two were “independent rather than redundant” was the defect, because a maintainer would reason from it that the two cover disjoint cases.
