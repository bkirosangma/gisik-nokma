## Filled from Plan 4's reserved range

- **6.5** ✅ `proj_memberships` resolves effective roles. A grant records who granted it, when, and at which stream position; a re-grant updates the role in place, one row per membership identity, carrying the later event; a revocation removes the workspace row so the role stops being conferred, and touches only the revoked user; project roster events add and remove project-scope rows carrying the project-admin flag, and a project removal leaves the workspace row and other projects standing. A non-member resolves to null with no projects; the newest grant wins; a revoked member resolves to nothing **though the roster row survives in the table**; a re-grant after a revocation restores the role; a role held in another workspace does not carry over. `hasProjectAdminRights`: owners and admins hold rights on every project including ones they are not on, a project admin on that project only, a plain project member none, a guest none even on a project they are on. **The determinism case is the load-bearing one** — live application and a rebuild from the ledger agree though the two orders differ — because the plan text's revoke handler failed exactly there. (`apps/server/test/proj-memberships.test.ts`, `apps/server/test/permissions/effective-role.test.ts`)
- **6.6** ✅ Admin-only event types are refused below admin with rule `permission.role`: `workflow.defined`, `ticket-type.defined`, `project.created` and `ticket.workflow_rebound` each refused to a plain member, and each allowed for both `owner` and `admin`. Ordinary ticket work is let through — the visibility gate (Task 9) owns the rest. (`apps/server/test/permissions/check-role-permission.test.ts`)
- **6.7** ✅ A claim submitted as another person is refused — including from a workspace owner, so the check is identity and not privilege. Identity is asked **first**, before any role is resolved. (`apps/server/test/permissions/check-role-permission.test.ts`)
- **6.8** ✅ A client-submitted event wearing the server's envelope-origin is refused, and founding a workspace appends the whole sequence server-side: the default workflow, then the four built-in types, then the grant, **in that order**, leaving its founder owning the workspace, founding on the canonical template itself rather than a copy that resembles it. Founding works through the client door too — the gate admits the founding and not the sequence. (`apps/server/test/permissions/check-role-permission.test.ts`)
- **6.9** ✅ Visibility resolution. A root that authored nothing resolves to the project default, authored by nobody (`resolved_from` empty); a ticket's own authored mode wins over everything above it and names itself as the author; an explicit list is carried through while a standing-audience mode carries none — **not by accident**, since the domain schema refuses `userIds` on a non-explicit mode, so a list there could only have been invented here; a chain walks to the **nearest authored ancestor**, and `resolved_from` names that ancestor rather than the immediate parent, which is the discriminator between copying the parent's `resolved_from` and copying its `ticket_id`; and a ticket whose parent row does not exist is treated as a root rather than dropped. (`apps/server/test/proj-visibility.test.ts`)
- **6.10** ✅ Re-resolution, pruning, and a rebuild that reads the ledger in the order a rebuild really uses. An ancestor's visibility change reaches every inheriting descendant; re-resolution **stops dead at an authored descendant and at everything under it**; a reparent moves the ticket and its subtree onto the new chain, and to root falls back to the project default; setting a ticket back to `inherit` re-attaches it and its subtree. **The determinism cases are the load-bearing ones, and they are deliberately not the plan's** — and they hold only while the parent graph is **acyclic**, which the case title says and case 6.58 measures. The plan's own rebuild test replays the same arrival order it applied, so it asserts only that `apply` is a function; these three seed the real ledger, assert that canonical order genuinely differs from arrival order, and compare live against a **rebuild** — enumerating a child created before its parent's row exists, an authored node pruning mid-chain, and a reparent-plus-set-back-to-inherit moving a subtree. The plan text's `ticket.created` handler fails the first of them. **The pruning line itself is an optimisation, not a fact these cases pin** — mutating it away leaves every test green, because re-resolving an authored node re-derives the value it already held; the property "an authored subtree cannot be reached from above" lives in the own-mode branch of `resolveOne`, and mutating THAT reddens eleven cases. Both the source and the covering test say so, in place of the comment that claimed the prune was load-bearing. (`apps/server/test/proj-visibility.test.ts`)

- **6.39** ✅ The owner reads everything in the workspace, including an explicit list naming only other people; an **admin** still reads nothing they have not joined or been listed for. The split IS the planted defect — a regression re-unifying the two roles fails one side or the other. The admin case carries its own **positive control** in the same test (an admin does see workspace mode, does see a project they joined, does see a list naming them), because "an admin sees nothing" would otherwise also pass if admins were being treated as non-members. (`apps/server/test/visibility/can-see.test.ts`)
- **6.40** ✅ An owner on **no project and no explicit list** receives every ticket from `listVisibleTickets` — from the bypass alone — and the SQL and the pure function agree **ticket by ticket for every viewer class**, not only for the owner: non-member, guest, member on project 1, member on project 2, admin on no project, owner, and a revoked member. Each class is asserted **twice over** — its exact expected id set, and the cross-check against `canSee` — because the cross-check alone agrees vacuously wherever both answers are empty, and the id sets alone would not notice a `canSee` that had drifted from the SQL. A non-vacuity assertion pins that the fixture is not one where everybody sees nothing. (`apps/server/test/visibility/visible-tickets.test.ts`)

## Minted by Tasks 4–6, anticipated by no plan document

- **6.43** ✅ The founding bypass cannot be used to seize an existing workspace. Three planted defects: a **non-member founding a workspace that already exists** is refused; **a stranger cannot become owner by re-founding**; and *"already exists" is a question about the WORKSPACE, not about one entity id* — the variant that defeats the obvious guard, because a founding filed under a **fresh entity id** against the victim's workspace passes both a head-row lookup and a per-entity `seq` check. The internal door does not re-found either, and re-founding with the same event id does not bootstrap a second time. This existed as a live escalation in the task's first commit: a stranger resolved as `owner` of a workspace they were never in, because nothing refuses a second `workspace.created` and the bootstrap then granted them ownership. (`apps/server/test/permissions/check-role-permission.test.ts`)
- **6.44** ✅ The gate reads the **ingest transaction's own connection**, never a second one from the pool — pinned against a pool that permits exactly one checkout, so a gate reaching for a second connection meets a planted error rather than deadlocking silently under load. (`apps/server/test/permissions/check-role-permission.test.ts`)
- **6.45** ✅ Project-roster changes are gated on **project-admin rights, not workspace membership**: a project admin manages their own project's roster and no other, is refused when they try to grant *workspace* membership, and a plain project member is refused roster changes outright. Workspace-scope membership grants are refused from below admin. (`apps/server/test/permissions/check-role-permission.test.ts`)
- **6.46** ✅ The gate reads roles through `resolveEffectiveRole`, so a **revoked member is refused at once** rather than at the next cache boundary; and the internal door is not gated — the same refused event commits through it, which is what proves the refusal belongs to the door rather than to the event. (`apps/server/test/permissions/check-role-permission.test.ts`)
- **6.47** ✅ The canonical simple-Kanban definition clones into a def that validates clean at version 1, and is **deep-cloned** — editing a clone never reaches the template. (`packages/domain/test/simple-kanban.test.ts`)
- **6.48** ✅ `POST /v1/events` answers `401 {error:'unauthenticated'}` with no session and **never reaches ingest**; a signed-in caller gets through, so a `requireSession` that refused everyone would not pass. (`apps/server/test/events-route.test.ts`)
- **6.49** ✅ A payload `proj_memberships` cannot honestly store is refused rather than written as `undefined`, and the schema refuses a scope that disagrees with its project id. `reset` empties the table it declares — pinned because an omitted `tables` entry is *destructive*, not merely unverified: the verifier makes no shadow copy, so the projection's `TRUNCATE` would hit live. A corrupted live row is reported against the ledger rebuild and live is left alone. (`apps/server/test/proj-memberships.test.ts`)

- **6.55** ✅ Every `proj_visibility` write is keyed on **the entity the event was filed against**, never on the ticket the payload restates. A `visibility.set` filed against ticket A whose payload names ticket B writes A's row and leaves B's untouched — the second assertion is the positive control, so "wrote the filed-against row" cannot be "wrote both". Keying on the payload would let one ticket's stream write another ticket's row, which is the cross-entity write that makes live application and canonical replay disagree; Task 9 owns refusing the disagreement itself. (`apps/server/test/proj-visibility.test.ts`)
- **6.56** ✅ The projection's own hygiene: a payload it cannot honestly store is **refused rather than written** — `visibility.set` with `explicit` and nobody named throws at the parse instead of storing an audience of nobody, which would hide the ticket for real; `seq` records the **per-entity** sequence of the ticket stream that authored the row and not the workspace cursor, pinned against a fixture that gives the two counters different values — and pinned **twice**, because a later `visibility.set` overwrites the column, so the creating handler's own write is only observable on a ticket that has never been touched again; an authored mode that is not `explicit` resolves to **no user list even when the row carries one**, checked on a hand-written row because `visibilitySetPayload` refuses `userIds` on those modes and so no event can produce that state — the guard was decorative until this case, and it matters because `resolved_user_ids` is what Task 7's `canSee` will read; `reset` empties the table it declares; an event type it does not read leaves the table empty; and a corrupted live row is **reported** against the ledger rebuild while live is left alone — the shadow-schema fence, asserted as a planted defect being caught rather than as "verify is clean", which an empty `tables` would also satisfy. (`apps/server/test/proj-visibility.test.ts`)

## Minted by Task 7, anticipated by no plan document

- **6.59** ✅ **The ruling, made falsifiable — and the half of it that could not be.** A member on a project is **revoked** from the workspace; their project-scope `proj_memberships` row is still standing, and the case **selects that row and asserts its contents**, not its count, because if the row were gone then `canSee` answering `false` would prove only that a missing row confers nothing. All three resolved modes are walked (`project`, `workspace`, and an `explicit` list that still names the revoked user by id), each asserted `true` *before* the revocation, so the `false`s after it are a change and not a fixture that never worked. **Measured, and it contradicts the obvious expectation:** the line that reddens this case is `canSeeResolved`'s null-role short-circuit, not `resolveEffectiveRole`'s empty-project-set early return — deleting that early return leaves all sixteen of Task 7's tests green, and leaves the entire server suite green but for Task 4's own `effective-role.test.ts` case “a revoked member resolves to nothing, though the roster row survives in the table”. Two guards stand on this path, and **on the ruling's own mode they are REDUNDANT, not independent** — measured one assertion at a time, which is the granularity the first write-up of this case lacked. Deleting only `canSeeResolved`'s null short-circuit fails `:232` (`workspaceMode`) while **`:231`, the project-mode revoked member, still passes**; deleting only `resolveEffectiveRole`'s early return fails nothing in this file; deleting **both** fails `:231`. So on the project-mode path either guard alone blocks the leak, and on the workspace-mode path — where no project set is consulted — only the short-circuit stands. Both are present and the code is correct; the earlier sentence claiming the two were “independent rather than redundant” was the defect, because a maintainer would reason from it that the two cover disjoint cases. The early return earns its keep for a different reason: it protects readers with **no null check of their own**, live example `hasProjectAdminRights`, which reads `eff.projects.get(id)?.projectAdmin` and would answer `true` for a revoked member whose surviving project row carries `project_admin = true`. **No test reachable from `canSee` can pin that early return**, because nothing can make the project set matter while the workspace role is null. Recorded that way rather than claimed: a case here asserting it had proved the ruling would be passing for a reason unrelated to the property it named. (`apps/server/test/visibility/can-see.test.ts`, and for the other guard `apps/server/test/permissions/effective-role.test.ts`)
- **6.60** ✅ A visibility answer is scoped to **one workspace**. `canSee` takes no `workspaceId` — it resolves the role in the workspace the ticket's own `proj_visibility` row names — so an **owner of workspace A is refused a workspace-mode ticket in workspace B**, with the owner of B as the positive control. `listVisibleTickets` is scoped the same way: an owner of two workspaces gets each one's tickets separately, and a member of one lists nothing from another **though the two use the same project id** — the fixture that defeats a project predicate standing without a workspace clause. (`apps/server/test/visibility/can-see.test.ts`, `apps/server/test/visibility/visible-tickets.test.ts`)
- **6.61** ❌ `listVisibleTickets` returns **`proj_visibility` rows, not ticket rows**. Plan 4's text has it joining `proj_tickets`; that table does not exist on this branch — Plan 3 Task 12 owns it — and Task 7 does not invent a migration for it, because a table this plan authored would be a second, competing definition of another plan's projection. The published contract is `Array<Record<string, unknown>>` and Task 8's route reads `ticket_id`, so nothing downstream is typed against the difference, but a caller wanting a **title** does not get one today. The change when `proj_tickets` lands is one `SELECT t.* FROM proj_tickets t JOIN proj_visibility v USING (ticket_id)` behind the same WHERE clause and the same tests. *Owner: Plan 3 Task 12 (the table), then Plan 4 Task 8 (the route that needs the columns).* (`apps/server/src/visibility/visible-tickets.ts`)
- **6.62** ✅ The decision table enumerated **by path**, pure: a non-member in all three modes including one that names them; a guest carrying a project attachment who still sees neither workspace nor project mode; a member on the project, off it, and on a *different* project; an admin with no bypass and its positive control; the owner from the bypass alone; and the **project-admin flag proven to be management and not reading** — a project admin is refused an explicit list naming somebody else and another project's project-mode ticket, while their own attachment still works. (`apps/server/test/visibility/can-see.test.ts`)
- **6.63** ✅ The same decision walked end to end through the **real projections and real event payloads**: guest, member and outsider on one explicit ticket; an unknown ticket invisible to everyone **including the owner**, because a missing row is answered before a role is resolved and the bypass is never reached; inherited visibility governing a child that authored nothing, with the **listed** member as the positive control against "the child is invisible to everybody"; a guest listing a child it inherited from an explicit ancestor while a workspace-mode ticket beside it stays out of the list; and an admin who sees a project's tickets **only after joining it**. (`apps/server/test/visibility/can-see.test.ts`, `apps/server/test/visibility/visible-tickets.test.ts`)
- **6.64** ❌ **Nothing enforces that an `EffectiveRole` came from `resolveEffectiveRole`.** `canSeeResolved` takes the value by parameter, and every safety property proved of it rests on that value having been produced by `resolveEffectiveRole` — which is the only thing that makes `workspaceRole === null` imply an EMPTY project set. That provenance is a convention today, not a constraint: `EffectiveRole` is a plain interface, so any caller can build one by hand or cache one across a revocation, and a third caller doing so would carry a project set no early return has emptied. **Stated as an absence, not as a measurement:** no test was run to construct such a value and observe a leak — what is recorded is that neither the type system nor any existing case would object if one did. The two callers on this branch (`canSee`, `listVisibleTickets`) both resolve in-line and are unaffected; the exposure begins with the third. The fix shape, so it is not rediscovered: brand the type so only `resolveEffectiveRole` can mint one, or take `(db, userId, workspaceId)` and resolve inside. *Owner: Plan 4 Task 8 — the first task that calls `canSee` from a route.* (`apps/server/src/visibility/can-see.ts`, `apps/server/src/permissions/effective-role.ts`)
- **6.65** ❌ **`listVisibleTickets` is compiler-exhaustive on the role but not on the mode.** The role dispatch is TypeScript and now reddens with TS2366 when `WorkspaceRole` grows, matching `canSeeResolved`; the three `resolved_mode` values are string literals inside a SQL string, which the compiler cannot see. A fourth mode would therefore fail to compile in `canSeeResolved` and fail **closed** in the SQL — excluded from every non-owner list — so the copies drift rather than leak. Only the per-viewer cross-check in `visible-tickets.test.ts` can catch it, and only if that fixture is extended to carry the new mode. *Owner: Plan 4 Task 8 (the route that consumes the list), or whichever task introduces a fourth mode.* (`apps/server/src/visibility/visible-tickets.ts`)

- **6.57** ❌ `proj_visibility.project_id` is written **only at `ticket.created`** and is never updated afterwards, because `ticketReparentedPayload` carries `newParentId` and nothing else. - **6.58** ❌ `proj_visibility` is order-independent **only while the parent graph is acyclic**, and nothing on this branch refuses a cycle. `resolveOne` reads the parent's *stored* resolution, so once `parent_id` closes a loop the invariant has several fixpoints and which one the table settles in depends on arrival order. Measured, not inferred: `created(G) · visibility.set(G,'workspace') · created(A,G) · created(B,A) · ticket.reparented(A,B)` leaves **live** at `workspace`/G for both A and B and a **rebuild** at `project`/`''` for both — two rows of drift that `verify-projections` would report against a table nobody corrupted. The projection terminates on the cycle (pinned) and claims nothing more; the covering test deliberately does **not** assert determinism there, because asserting it would be the check that passes for the wrong reason. Plan 3's reparent command does not exist yet and the permission gate does not look at ancestry, so the cycle is reachable today. The fix shape, so it is not rediscovered: have `resolveOne` walk up to the nearest authored ancestor rather than read the parent's stored value, making resolution a function of the current graph loop or no loop. *Owner: Plan 3 (refusing a cycle-creating reparent at the door), or Plan 4 Task 9's check list.*
