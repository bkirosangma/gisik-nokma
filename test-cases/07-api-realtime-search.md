- 7.3 ✅ `filterSpecSchema` refuses unknown keys, bad ops, malformed dates, empty identifiers and oversized inputs while accepting its own boundaries, and keeps hostile bytes intact rather than sanitising them; `groupingSchema` admits exactly five groupings. (`packages/domain/test/filter-spec.test.ts`)
- 7.4 ✅ Planted defect: a hostile fieldId/text term never reaches SQL text — the compiled clauses are pinned as a CONSTANT, identical for all thirteen hostile inputs sent through all seven slots, and the parameter array is asserted by exact equality (every slot's value once, in order, plus the escaped LIKE pattern). Stated this way on purpose: the earlier `expect(sql).not.toContain(value)` measured whether a value LOOKED LIKE SQL and reddened on a correct compiler for `$1`, `t.`, `SELECT`, `->>` or `ESCAPE` — all five are now in the hostile set precisely so a regression to that form fails. (`apps/server/test/read/compile-filter.test.ts`)
- 7.46 ✅ The compiled filter is EXECUTED against Postgres with thirteen hostile inputs through every slot — a bare quote, a statement terminator with `DROP TABLE`, a comment marker, an always-true tautology, a balanced-parenthesis subquery, a Unicode-escape payload, `DELETE FROM events`, a 500-character string, and five look-alikes a correct compiler emits verbatim (`$1`, `t.assignee_id`, a `SELECT … FROM proj_search`, `->> 'value'`, `ESCAPE '\'`). Each returns empty where empty is the truth; the same hostile bytes sent as the field id and value that genuinely exist on a seeded ticket MATCH it, which is the positive control that makes those empties evidence rather than an artefact; `proj_tickets` and `events` survive with unchanged counts; and `websearch_to_tsquery` (never `to_tsquery`) keeps a hostile text term a phrase rather than a syntax error. (`apps/server/test/read/compile-filter.test.ts`)
- 7.47 ✅ The blocked-state filter answers from the ticket's own workspace. A second workspace holding the same `workflow_id` at a higher version — which `proj_workflows`' `(workflow_id, version)` primary key permits — does not decide which of the first workspace's tickets read as blocked; and every compiled clause that reaches another table is asserted, term by term, to carry the `workspace_id = t.workspace_id` correlation. (`apps/server/test/read/compile-filter.test.ts`)
- 7.48 ✅ LIKE metacharacters inside a `contains` value are literal: `50%_done` matches the ticket claiming exactly that, while the wildcard reading `5%d` matches nothing. (`apps/server/test/read/compile-filter.test.ts`)
- 7.49 ✅ U+0000 is refused at the door in all seven free-form string slots (`assigneeId`, `collaboratorId`, `typeId`, `stateId`, `text`, `fields[].fieldId`, `fields[].value`), with a message naming the reason; `due.before`/`due.after` need no separate guard because their `\d`-class regex already refuses it, asserted rather than assumed. Past the door the same seven specs each raise SQLSTATE **22021** against the live database — the compiler parses, compiles and binds them correctly, so the schema's refusal is what keeps a schema-valid FilterSpec from becoming a 500. The same seven specs with the NUL removed pass the door and execute. (`packages/domain/test/filter-spec.test.ts`, `apps/server/test/read/compile-filter.test.ts`)
- 7.50 ✅ ONLY U+0000 is refused: BEL, TAB, LF, CR, ESC, DEL and a lone surrogate all parse and are returned unchanged, because Postgres carries every one of them through `text` and `websearch_to_tsquery` — the door's rule is "what the store can hold", not a taste for tidy input, and a multi-line pasted search term stays legal. (`packages/domain/test/filter-spec.test.ts`)
- 7.51 ✅ A concatenated `fieldId` is shown to WIDEN a result set, not merely to break: a deliberately unsafe reference compiler in the test interpolates the id, and the payload `amount' ->> 'value' IS NOT NULL OR '1'='1' --` comments away the tail and defeats the caller's workspace scope by precedence, returning another tenant's ticket. The real compiler answers `[]` for the same bytes, and the paired control — the unsafe compiler on a benign field id returning exactly what the real one returns — makes the widening evidence about the payload rather than about the reference compiler. (`apps/server/test/read/compile-filter.test.ts`)
- 7.52 ✅ The `proj_search` tenancy correlation is executable, not merely asserted as a string: a WS_A ticket whose search row is MIS-FILED under WS_B is not found by a WS_A text search, while the same query with `workspace_id = t.workspace_id` deleted returns it, and the row is separately shown to exist and match the term. Projection drift is the reachable failure — `proj_tickets.ticket_id` is globally unique, so a correctly-filed neighbouring row can never answer out of the wrong tenant and seeding one would redden nothing. (`apps/server/test/read/compile-filter.test.ts`)
- 7.53 ✅ `fields[].value` carries no `.min(1)` and the consequence is declared and executed: `eq: ''` matches only the ticket whose field IS the empty string; `contains: ''` compiles to `ILIKE '%%'` and is a field-PRESENCE predicate — it matches the empty value and a non-empty one, and matches nothing for a key no ticket carries or a key present with a JSON null value, so it cannot widen a read. `fieldId: ''` stays refused. (`packages/domain/test/filter-spec.test.ts`, `apps/server/test/read/compile-filter.test.ts`)
- 7.54 ✅ A due bound constrains day SHAPE, not calendar existence: `9999-99-99` and `2026-02-30` are admitted (fixed-width zero-padding is what makes the compiled text comparison chronological, and a stricter filter than the storage schema would refuse a bound the store holds), while `2026-8-1` and a datetime stay refused. The pattern is `IST_DAY_REGEX` imported from `ist-day.ts`, not a second spelling of it. (`packages/domain/test/filter-spec.test.ts`)
- 7.55 ✅ `workspaceSettingsSetPayloadSchema` accepts either knob alone or both together, refuses the empty claim (neither key present), and refuses unknown keys, non-integers, and out-of-range values for both `staleDays` and `dueSoonDays`. (`packages/domain/test/events/workspace-settings.test.ts`)
- 7.56 ✅ A well-formed `workspace.settings_set` v1 envelope round-trips `parseEvent` as `ok: true`; a malformed payload (empty claim) is refused with `code: 'invalid-payload'`. (`packages/domain/test/events/workspace-settings.test.ts`)
- 7.57 ✅ Planted-defect proof that the registration's `entityKind: 'workspace'` is load-bearing rather than decorative: a `workspace.settings_set` envelope whose `entity.kind` is `'ticket'` is refused by `parseEvent` with `code: 'entity-kind-mismatch'`, not admitted — `parsed.ok === true` alone cannot show this, since the registration's `entityKind` field is optional and every other value (including omitting it) also passes the round-trip case. Falsifiability checked by removing `entityKind: 'workspace'` from the registration and confirming this case (and only this case) reddens, then restoring it. (`packages/domain/test/events/workspace-settings.test.ts`)
- 7.58 ✅ `checkRolePermission` on `workspace.settings_set`: workspace `owner` and `admin` are admitted (`null`); `member`, `guest` and a non-member (`workspaceRole: null`) are all refused `{refused: true, rule: 'permission.role', reason: 'Only a workspace owner or admin can change workspace settings.'}` — the planted-defect case pins the exact rule and reason text, not merely that a refusal occurred. (`apps/server/test/permissions/settings-permission.test.ts`)
