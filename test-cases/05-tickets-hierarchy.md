- 5.38 ✅ A second `ticket.created` for a ticket that already exists is refused `ticket.already-exists`, ahead of every question about its payload. The order is pinned separately: a duplicate create whose type is ALSO undefined still names the duplicate, because the actor's type was never the problem. - 5.39 ✅ Two refusals that used to fire with somebody else's sentence now tell the truth on the path that reaches them. A parent whose TYPE is undefined refuses `hierarchy.parent-type-unknown` naming the parent, not `ticket.unknown-type` — this ticket's own type resolved, so the borrowed copy sent the actor to define a type that is already defined (ruling P11). A parent in ANOTHER WORKSPACE refuses `hierarchy.unknown-parent`, not `hierarchy.cross-project`: ticket lookup carries no workspace predicate over a projection keyed `(entity_kind, entity_id)`, so a foreign parent resolves, and the more specific sentence was both false and a confirmation that the id exists somewhere the actor cannot see (ruling P12). Both are pinned as literals and mutation-proven, and the workspace case is staged against a parent that is foreign in project too, so the order is what the test constrains. (`packages/rule-engine/test/hierarchy.test.ts`)
- 5.40 ✅ Reparenting inherits both rulings the create path was corrected by, and its check ORDER is pinned rather than described. A parent whose type is undefined refuses `hierarchy.parent-type-unknown` naming the parent — Task 6's brief specified `ticket.unknown-type`, which is false on every path that reaches it because the MOVED ticket's own type resolved first (ruling P11) — while a ticket whose own type is missing still refuses `ticket.unknown-type`, because there the sentence is exactly true. A parent in another WORKSPACE refuses `hierarchy.unknown-parent`, not `hierarchy.cross-project`: the brief had no workspace guard at all, and a reparent grafts an EXISTING ticket into another workspace's hierarchy rather than merely failing to make a new one (ruling P12). Seven order cases stage two live defects each and assert which names the event — the ticket's own absence outranks the parent's; a loop is named as a loop even when the rank is violated and even when the parent is in another project; a foreign workspace outranks a foreign project; cross-project outranks an unreadable parent type; cross-project outranks a rank violation; rank outranks a finished parent. The cross-project-over-unreadable-parent-type pairing is also added to `checkTicketCreated`, closing the one chain position Task 5 left prose-pinned: a mutation hoisting the parent-type guard above the cross-project check passed the entire suite until now. (`packages/rule-engine/test/reparent.test.ts`, `packages/rule-engine/test/hierarchy.test.ts`)
- 5.41 ✅ An ancestor chain that never ends THROWS rather than refusing, staged against two tickets that are each other's parent and neither of which is the ticket being moved. The distinction is deliberate: a malformed payload is the actor's claim and is refusable in the actor's language, while a cycle already standing in the tree is the store's state — this check is what prevents one — so there is no true sentence to tell the actor, and `hierarchy.cycle` would name a loop that is not the one they proposed. (`packages/rule-engine/test/reparent.test.ts`)
- 5.42 ✅ `evaluateEvent` actually routes the three new event types. (`packages/rule-engine/test/reparent.test.ts`, `packages/rule-engine/test/workflow-rebind.test.ts`, `packages/rule-engine/test/ticket-type.test.ts`, `packages/rule-engine/fixtures/type-defined-*.json`)
- 5.43 ✅ A `ticket.workflow_rebound` naming a workflow this workspace has not defined is refused `ticket.rebound-unknown-workflow`, whose reason names **that** workflow and offers the two remedies an admin can take alone. It is deliberately not `ticket.workflow-undefined` — "This ticket type's workflow has not been defined yet, so the ticket would have no status." — which makes the ticket TYPE's binding its subject: correct on `ticket.created`, where a ticket has no workflow but the one its type names, and false on a migration, where the binding may be perfectly well defined and the missing workflow is the one the payload asked for. The old sentence sent an admin to inspect a thing that was not broken. The test asserts the premise as well as the refusal — the ticket's own type binding resolves in the same context, so the borrowed sentence was false of the world it was told in. Controller ruling P13, the third instance of the class P11 and P12 closed. **Task 14 folds this into case 5.34**, whose plan text this change set corrected in place (same number — 5.34 is cited only inside Plan 3's own document, unlike 5.27/5.30/5.36). (`packages/rule-engine/test/workflow-rebind.test.ts`)
- 5.44 ✅ A `ticket.field_set` whose payload omits `value` entirely is refused at the door, not folded into a clearing. `z.unknown()` does not require its key, so `{ fieldId: 'title' }` parsed clean, and the reducer's then-`p.value ?? null` turned that absence into a null CLEARING claim — a field wiped under someone's name and both their clocks, into an append-only table, on the strength of a claim nobody made. Four assertions rather than one "the field is required", because two of them are ACCEPTANCES and they are the half a careless fix breaks: `null` is the explicit clearing claim and `{}` is an empty claim, both still claims. Proven by reverting the schema to bare `z.unknown()` and watching the ABSENT case fail specifically — a mutation that killed only the present-but-`undefined` case would have proven a side effect of the fix rather than the fix. The identical matrix guards the envelope's own payload (`packages/domain/src/envelope.ts`), so the two doors answer alike. **Task 14's 5.12 stays the home for the field refusals the plan anticipated** (unknown field, per-kind mismatch, the title that cannot be cleared); this id covers only the presence hole, which no plan document names. The coalesce itself is gone as well (case 5.50): with the key required, `parse` throws before the fold and `null ?? null` is identity, so `packages/domain/src/ticket-state.ts:211` now reads `claim(p.value, env)`. (`packages/domain/test/ticket-events.test.ts`, `packages/rule-engine/test/fields.test.ts`)

- 5.48 ✅ A `ticket.created` whose title is only spaces is refused at the door, and a padded real title is stored VERBATIM. `z.string().min(1)` admitted `'   '`, so the create door was letting in precisely the state the edit door forbids — `checkTicketFieldSet` refuses a whitespace-only title change with `field.type-mismatch`, which made "the title that cannot vanish" an edit-time rule rather than an invariant, and a blank title one that could be created but never set. It REFUSES rather than trims, matching the treatment `workspace.created`/`workspace.renamed`/`project.created` already ship for their names: the ledger stores the claim as it was made, so rewriting `'  Reconcile the till  '` would put words in the actor's mouth. Four assertions, because two are ACCEPTANCES and they are the half a trimming "fix" breaks — the padded case asserts the stored string byte for byte. Proven by removing the refine and watching only the whitespace-only case (and its `parseEvent` twin) fail; the empty-title case stays green on `.min(1)`, which is what makes the mutation specific. Controller ruling P15. (`packages/domain/test/ticket-events.test.ts`)
- 5.49 ✅ A malformed-payload refusal names the FIELD it is about. Every check that parses a payload built its detail from `issue.message` alone and dropped the zod path, and a zod message is a subject-less fragment: `ticketCreatedPayload` has two ULID fields and refused a bad `parentId` with "must be a ULID"; a rebound with an empty `toStateId` said "String must contain at least 1 character(s)", where a reader guesses `toWorkflowId` first; and the presence refine produced a whole sentence about nothing. One shared `malformedPayloadDetail` now renders `at <path>: <message>` per issue, mirroring `parse-event.ts`'s construction so the door and the engine say the path the same way, and omitting the clause when the path is empty. All seven call sites route through it — `ticket.created`, `ticket.reparented`, `ticket.field_set`, `ticket-type.defined`, `ticket.workflow_rebound`, `ticket.transitioned`, `workflow.defined` — and one mutation of the helper turns all seven red at their own assertions. The nested-path case (`comment.text`) is the only assertion in the repo pinning the dot join, and the not-an-object case is the only one pinning the empty-path omission; the two shipped fixtures assert only the prefix that stops at "malformed:", which is unchanged byte for byte. (`packages/rule-engine/test/engine.test.ts`, `packages/rule-engine/test/hierarchy.test.ts`, `packages/rule-engine/test/reparent.test.ts`, `packages/rule-engine/test/ticket-type.test.ts`, `packages/rule-engine/test/workflow-rebind.test.ts`, `packages/rule-engine/test/fields.test.ts`)
- 5.50 ✅ The reducer's `p.value ?? null` is gone, and the four comments that described the fold as live now say what used to happen — plus a fifth reference that had come to dangle. Once `ticketFieldSetPayload` requires `value` (case 5.44) the coalesce is unreachable — the `parse` above it throws on an absent or `undefined` value, `null ?? null` is identity, and `claim(value: unknown, …)` never needed it for typing — so keeping it would state the defect as the design, the same reasoning that dropped the identical coalesce in `checks/fields.ts`. Covered by Task 3's own reducer suite, which exercises this fold and stays green. Deliberately NOT changed: the fixture harness's matching `payload.value ?? null` is still reachable, because the harness's prior-event schema is still bare `z.unknown()` — that pair belongs to Task 8 (pre-flight Addendum 7a). (`packages/domain/test/ticket-state.test.ts`)
