# Notes — Plan 2 of 6: Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver note events to exactly the devices whose user may read the note, take them away when reach is lost, backfill history when reach is gained (including through a ticket's visibility change), and hold notes in the client replica so desktop and mobile have the data and the web app's reads work offline.

**Architecture:** The server's stream classifies note events under a new audience class `note` and yields each event only when `canReadNote` holds; widening emits the existing `reach-granted` notice with a new `notes` arm, and the client pulls the note's history through a new bootstrap route. **Narrowing is client-driven**, as it is for tickets: the repo's ruling P23 forbids server-initiated per-entity purges, so the reconcile endpoint learns to answer for held note ids and the client purges from that answer. The replica gains `notes` and `note_comments` tables folded by the same `applyNoteEvent` the server uses, and `ReplicaDataSource` answers the seven note reads locally.

**Tech Stack:** Fastify + `pg` stream generator, WebSocket hub, `better-sqlite3` replica in `packages/sync-client`, vitest, the dual-client rig in `apps/server/test/dual-client/`.

**Spec:** `docs/superpowers/specs/2026-09-23-notes-design.md` §5 (and §2.4 of the brainstorm's sync section). **Deviation from the spec, recorded here:** spec §5.1 says "else if `isNoteRevokeTrigger` → yield purge". This repo does not emit server-initiated per-entity purges (the comment block inside the ticket branch of `apps/server/src/visibility/visible-events-for.ts` records the removed walk — search `6.101`; ruling P23). Notes follow the repo: narrowing reaches a device through `POST /v1/sync/reconcile`, which the client already runs on every catch-up. The property the spec wants — a device holds no note its user cannot read — is asserted in §11.4's cases against this mechanism.

**Depends on:** Plan 1 merged into `release/notes` (`canReadNote`, `loadNoteForVisibility`, `canReadNoteById`, `getNoteStateFromDb`, `proj_notes`, `proj_note_attachments`, `proj_note_comments`, the seven `DataSourceQuery` note methods with `NOTES_ABSENCES` gap entries, and the notes fixture `apps/server/test/helpers/notes-fixture.ts`).

export const NOTE_GRANT_TRIGGERS = ['note.created', 'note.scope_set', 'note.attached', 'note.restored'] as const;
export function isNoteGrantTrigger(type: string): boolean { return (NOTE_GRANT_TRIGGERS as readonly string[]).includes(type); }

export async function noteGrantNoticeFor(
  db: Queryable, userId: string, noteIds: readonly string[], afterSeq: number, backfilled: Set<string>,
): Promise<ReachGrantedNote[]> {
  const eff = await resolveEffectiveRole(db, userId, /* workspace of the first note */ (await getNoteStateFromDb(db, noteIds[0]!))!.workspaceId);
  const admitted: string[] = [];
  for (const id of noteIds) {
    const key = `note:${id}`;
    if (backfilled.has(key)) continue;
    backfilled.add(key);
    const loaded = await loadNoteForVisibility(db, id);
    if (loaded === null || !canReadNote(eff, userId, loaded.note, loaded.attachedVisibilities)) continue;
    admitted.push(id);
  }
  return withNoteHeadSeq(db, admitted, afterSeq);
}
