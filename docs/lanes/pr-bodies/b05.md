### Follow-up verification, after `DONE B05` was printed

Three things this batch claimed in prose but had not measured, checked afterwards. Two held; the third found a real hole that is now closed.

- **E4-17's docblock says the fix is "inert by construction" for the searchable branch.** Measured: with focus in the searchable input and the panel open, `document.activeElement` is the `INPUT` both before and after Escape — focus never leaves it (virtual focus, as the judge's note said), so `FocusScope`'s restore condition is never met. The claim holds. Not committed as a test; the probe was throwaway.
- **P8's docblock says a close that moves focus somewhere deliberate is not overridden.** Measured: clicking a control outside an open Select moves focus to that control (`Elsewhere`), and the trigger is *not* re-focused. The claim holds.
- **The hole: P8's `contain` and a portalled popover fight, and E4-17 is what stops them.** A `Select` panel portals to `document.body`, i.e. outside the panel in the DOM, so containment reads the option row as an escape. Measured both ways — with E4-17's `FocusScope` on `SelectPanel`, focus lands on `li.gn-select__option`; removing it leaves focus on `button.gn-select__trigger` with the row never focused, inside *every* dialog in the product. The mechanism is React Aria's scope tree, not the DOM: the panel's scope is a child of the dialog's through React context, which crosses the portal, so `isElementInChildScope` answers true. **Nothing in the batch covered this**, and it would break silently, because the panel's `FocusScope` reads as a redundant wrapper from either half on its own. A sixth P8 case now pins it, mutation-witnessed to redden exactly when that `FocusScope` is removed.
