### `T-P12` — THE FIRST FIX DID NOT WORK, AND THE OWED READING IS WHAT FOUND IT

**`0e99bedf` shipped a fix that lands on zero of its client routes, and its suite was green throughout.**
The correction commit carries the rework; this section is the account, because the row above would
otherwise claim something measured as false.

The first version gave each `'use client'` route a `<DocumentTitle>` whose effect writes `document.title`,
and asserted only that the mechanism was DECLARED. **Traced in Chrome against the built app**, forwarding
`document.title` setter plus a 20 ms poll of the real value:

```
  /sign-in   atMs  0  value ""                        ← no <title> yet
             atMs 21  set   "Sign in · Gisik Nokma"   ← the effect
             atMs 21  value "Sign in · Gisik Nokma"   ← it took
             atMs 42  value "Gisik Nokma"             ← REACT PUT IT BACK
             finalTitle after 15 s: "Gisik Nokma"
  /help      setter at 127 ms; finalTitle after 4 s: "Gisik Nokma"
```

The 42 ms repair **does not go through the `title` setter** — React mutates the `<title>` NODE while
hydrating Next's `<head>`, repairing the text it finds changed under it. A jsdom arm can see the
mechanism and cannot see this, which is precisely why the browser reading was recorded as owed.

**Two replacements were tried and are MEASURED FAILURES**, recorded so neither is re-attempted (both in
`src/document-title.tsx`): a `useSyncExternalStore` hydration gate — the write still landed at 21 ms,
because React repairs *after* hydration of the subtree, so no hydration signal precedes it — and
returning `<title>` for React 19 to hoist, which produced **three** `<title>` elements in the hydrated
document (`["Gisik Nokma", "Sign in · Gisik Nokma", "Gisik Nokma"]`); React does not deduplicate them and
`document.title` reads the first, which is Next's. **Strictly worse.**

**What holds: a SERVER route-segment `layout.tsx` exporting `metadata`.** A segment layout is a server
component even when the page beneath it is `'use client'`, so the title reaches the head **before any
JavaScript runs** — which is what WCAG 2.2 §2.4.2 (Level A) actually asks for. `<DocumentTitle>` survives
ONLY where the topic resolves from a READ (the workspace and project names), whose writes land long after
the repair; each of those keeps a server layout for the generic title shown meanwhile.

**MEASURED — `/tmp/b03-tp12-served-titles.log`.** Served, each route carrying its own:
`/sign-in` → `Sign in · Gisik Nokma` · `/help` → `Help · Gisik Nokma` · `/inbox` → `Inbox · Gisik Nokma`
· `/account` → `Account · Gisik Nokma` · `/settings` → `Settings · Gisik Nokma` · `/workspaces` →
`Workspaces · Gisik Nokma` · `/privacy` → `Privacy · Gisik Nokma` · `/terms` → `Terms · Gisik Nokma` ·
`/mcp/tokens` → `MCP tokens · Gisik Nokma` · `/definitely-not-a-route` → `Page not found · Gisik Nokma`.
**Post-hydration in Chrome — the owed reading, now paid:** `/sign-in`, `/help` and the 404 each have
**exactly one `<title>`**, correct at the FIRST sample and unchanged across 4–6 s of polling. That the
404 works at all also proves **Next honours `metadata` in `not-found.tsx`**, a file its docs do not list.

The sweep was tightened in the same commit rather than left describing the old shape: it now requires
