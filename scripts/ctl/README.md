# scripts/ctl — the controller's mechanical work as verbs (owner's order, 2026-09-21)

`scripts/ctl/ctl <verb>` is the only door for: landing a PR, the forced gate, opening a PR, anchoring the controller state, verifying a batch PR, reconciling the ledger, watching lanes (`ctl seats [--flag]`: one read-only line per tmux seat — busy/idle, monitors, input box, Ctx, branch, last DONE/CHECKPOINT; `--flag` lists only seats needing action), restarting an executor, closing an idle lane (`ctl close <window>`: refuses the controller, the planner, a running turn, and a dirty or unpushed worktree), delivering a message to a pane, rebuilding the dev stack. A PreToolUse hook (`hooks/ctl-scripts-only.py`) refuses the raw forms in every Claude Code session on this machine; `ctl help` lists the verbs, each prints one summary line last (`OK …` / `FAIL …`), exits 0 only when every named condition held, and takes `--dry-run`.

## The marker chain
`ctl check-pr <branch>` (green) writes `.git/ctl/checked-<sha>`; `ctl pr open --require-checked` refuses without it. `ctl gate <sha>` (green) writes `.git/ctl/gate-<sha>`; `ctl land <pr>` refuses without it and re-reads the PR head at the instant of merging. A marker names one sha; a new commit needs a new run. `ctl gate` first fetches `origin/main` and refuses unless HEAD already contains it — a `--merge` landing is then content-identical to the gated head (otherwise the merge commit's tree is a union the gate never saw); merge `origin/main` into the branch and re-gate.

## `--base <branch>` — the integration ref (default `main`)
A merge to `main` deploys to production; work integrates on a `release/<name>` branch. `ctl gate`, `ctl land` and `ctl check-pr` take `--base <branch>` and measure against `origin/<base>` instead of `origin/main`. **Only `main` or `release/<name>` is accepted** (a task branch, `develop`, `release/`, `release/../main`, an empty value all refuse before anything runs).
- **`ctl gate <sha> --base B`** — fetches `origin/B` and refuses unless HEAD contains it (the remedy it prints names `origin/B` and repeats `--base B`). Green writes the marker `gate.release+<name>-<sha>` (`/` → `+`), **not** `gate-<sha>`.
- **`ctl land <pr> --base B`** — the PR's base must EQUAL `B` (checked at the start and again at the instant of merging, so a PR retargeted after the checks is refused), the gate marker must be the one for `B`, the ancestry re-read, the reachability, tree-identity and drop checks all read `origin/B`, and the primary checkout is fast-forwarded only when it stands on `B`.
- **`ctl check-pr <branch> --base B`** — the diff and the commit list are taken against `origin/B`; green writes `checked.release+<name>-<sha>`. **`ctl pr open --base B --require-checked`** looks for the marker of that same base.
- **Why main cannot be reached this way.** The default is `main` and its behaviour, its `gate-<sha>` / `checked-<sha>` marker names and its refusal messages are unchanged. A release-kind marker satisfies no landing or PR to `main`, and a `main`-kind marker satisfies none to a release branch; `land` merges only a PR whose base equals `--base`, so `--base release/x` can never merge into `main`. Landing into `main` is still the owner's word, per merge: run `ctl land <pr>` (no `--base`) only when they have said so.
- Known limit: `check-pr` still reads the plan and progress file it was always given (`--plan FILE`; the progress path is `docs/lanes/release-2026-09-22-progress.md`), so a release branch that does not carry them needs them supplied or the batch conditions do not apply.

## `ctl tipmerge` — the clean tip merge (owner-approved 2026-10-03)
`ctl tipmerge <branch> --base release/<name> --expect <sha> [--repo W] [--dry-run]` merges `origin/<base>` into `origin/<branch>` with no working tree: `git merge-tree --write-tree` computes the tree; if CLEAN the verb creates the merge commit (parents: branch tip, base tip), proves its tree and parents from the object database, pushes it to `<branch>` with a plain fast-forward push and re-reads origin with `ls-remote`; the last line is `OK tipmerge <branch> <sha40> …` and names `ctl gate <sha> --base <base>` (gate needs a checkout whose HEAD is that sha: from the gate checkout, `git fetch origin && git checkout --detach <sha>`; the lane's local branch is now behind origin — a lane that commits on it again must `git pull --ff-only` in its OWN worktree first, else its plain push is refused as non-fast-forward, which is safe). If CONFLICTED it prints `CONFLICT <path>` lines and exits **3**, pushing nothing — that case, a hand-resolved file, still goes to a lane and a reviewer fast path. `--expect` is **required** (7–40 hex: the READY sha); a branch that moved since is refused (exit 1). `<branch>` can never be `main`, any `release/*` name (even one that is no valid integration-branch name, such as `release/-x`) or `HEAD`; a failed fetch is a FAIL. A branch that already contains the base is `OK … already contains`, with no commit. `--dry-run` fetches and reports the verdict and the tree, creating and pushing nothing.

## The escape hatch
Set `GISIK_CTL_UNLOCK=1` in the environment of the `claude` process you launch (`GISIK_CTL_UNLOCK=1 claude …`) and the hook stands down for that session. A `GISIK_CTL_UNLOCK=1 gh pr merge` typed inside a session does not unlock (the hook's own environment is unchanged — case 32 of the self-test). Your own terminal runs no hook.
